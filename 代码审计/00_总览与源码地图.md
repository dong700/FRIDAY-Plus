## 0. 一句话说清这个项目

**FRIDAY Plus 是一个跑在本机的桌宠 Agent：Electron 挂一个 Live2D 立绘窗，背后是一个 FastAPI 服务，
它自己看屏幕、自己记事情、自己挑时候说话，用户也能直接跟它聊。**

三条硬边界（用户反复确认过，代码里也已经落实）：

1. **没有副脑**。`subbrain_demo/`、`state_core/`、`TFGRActivityBridge` 已删除；本项目里不存在"第二个大脑"进程或包。
2. **没有 Pro**。Pro（豆包实时语音那一套）已经独立上传 GitHub，Plus 不再 import 任何 `Pro`/`pro` 目录，也不共享运行时数据。
3. **不用本地大模型做判断**。本地只做 embedding（Ollama `nomic-embed-text` 768 维）与图像编码；所有"要不要说、记不记"的判断走规则或远端 LLM。

## 1. 进程与端口

| 进程 | 端口 | 入口 | 职责 | 起不来会怎样 |
|---|---|---|---|---|
| 后端（本体） | 18080 | `backend/run_server.py` | FastAPI：全部 HTTP + WebSocket + 业务 | 页面能开，但一句话都不会回 |
| 页面 + 反代 | 18090 | 根 `server.py` | 服 `ui/` 四个单页；`/api` 转发 18080；`/ws` 双向桥接 | 控制台打不开；桌宠仍可用（它直连 18080） |
| 桌宠窗 | — | `electron/main.js` | 加载 `http://127.0.0.1:18080/?pet=1` | 只剩控制台 |
| 语义库 | 18095 | `openviking-server`（外部） | 本地语义检索，embedding 打 11434 Ollama | 检索失败降级为空，不阻塞对话 |

**为什么桌宠走 18080、控制台走 18090**：桌宠只需要"对话 + 立绘"，直连后端延迟最低；控制台要四个页面 + 反代，单独一个进程方便热改 `ui/`。

**启动链**（真实文件，不是示意）：

```
start_pet.vbs
 ├─ wscript start_plus.vbs               # 起 18090（页面/反代）
 ├─ 18080 未监听 → powershell scripts/start_plus_backend.ps1
 │     └─ python -u run_server.py
 │           ├─ _bind_console_to_log()   # os.dup2 把 fd 1/2 接到日志
 │           └─ from api.server import app → uvicorn.run(ws="wsproto")
 └─ electron electron/main.js --url=http://127.0.0.1:18080/?pet=1
```

## 2. 数据流：一句话从键盘到气泡

```
用户打字
  → 前端 ws.send({type:"chat.send", payload:{content, client_msg_id}})
  → 根 server.py /ws 双向 pump（控制台）；桌宠直连 18080
  → backend/api/server.py websocket_endpoint → handle_client_event → handle_chat_send
       ├─ 存用户消息 + 广播 chat.message
       ├─ 负反馈：tfgr.penalize_recent(content)
       ├─ 规则提醒：_parse_reminder → tfgr.remember(due_at)
       ├─ 一次 LLM 决策：_brain_quick_decide（搜索 / 跑任务）
       ├─ 并发拿材料：视觉、搜索、Viking 记忆
       ├─ 拼 _blocks：提醒 → 最近 3 条回复 → 重复问题 → OV 命中 → 图片
       │                → 记忆 → 搜索 → 工具结果 → 屏幕观察 → TFGR digest
       ├─ _build_chat_messages(content, history, extra_context)
       ├─ llm.chat_stream → StreamFilter 过滤 <memory>/钩子 → mind.delta 流式
       ├─ 复读闸门：与最近 3 条重合 ≥0.9 → 重写
       ├─ 提醒生命周期：回复命中 → mark_done
       ├─ 结构化记忆：<memory> → ATG / TFGR
       └─ 钩子：<<after/idle/on>> → Mind.add_hook
  → 广播 chat.message(assistant) + avatar.speaking
  → 前端渲染气泡，Live2D 说话
```

主动说话是另一条独立链路：`Mind` 事件循环醒来 → `_should_speak` 五道闸 → 流式说话 → `mind.say` 广播。

## 7. 三个必须先记住的结论

1. **对话延迟的大头不是 LLM，是材料准备**。`_brain_quick_decide` 一次模型调用 + Viking 检索 + 可选九宫格，三件事任何一件串行都会多 2–6 秒。所以代码里到处是 `_want_screen` / `_want_image` 这种"按需才做"的开关——它们是性能设计，不是功能设计。
2. **记忆系统的核心不是"存"，是"挑"**。`digest` 的五层顺序 + query 相关度 + 粘性 + 跨来源去重，决定了模型这一轮看到哪 10 条；`importance` 的半衰期决定了旧判断会不会永远霸屏。
3. **主动说话的难点不是"说"，是"忍住"**。`_should_speak` 的五道闸 + `Mind` 的到点提醒优先级，是用户"别抢麦/别复读/别打断工作"诉求的最终落点。
