## 1. 进程入口：`backend/run_server.py`（全文 55 行）


### 逐段解析

| 行 | 为什么必须有 |
|---|---|
| `sys.path.insert(0, BACKEND_DIR)` | `backend/` 不是安装包，`api`/`brain`/`core` 是平铺目录，不插 path 就 `ModuleNotFoundError` |
| `os.chdir(BACKEND_DIR)` | 大量代码用相对路径 `Path("data")`、`Path("ui")`；不改 cwd，从任何目录启动都会找错 |
| `setdefault("PYTHONUTF8","1")` | Windows 控制台是 GBK，中文日志直接 `UnicodeEncodeError` 崩进程 |
| `os.dup2(f.fileno(), 1)` | **关键**：把进程级 fd 1/2 指向日志文件。必须在 `import api.server` **之前**，因为 logger 的 handler 在导入期绑定 stdout |
| 重新包 `sys.stdout` | fd 被 dup2 后，Python 层的 `sys.stdout` 还指向旧对象；uvicorn 的 formatter 会调 `.isatty()/.fileno()`，不换会抛异常 |
| `ws="wsproto"` | 环境里 websockets 16 与旧 uvicorn 握手不兼容，不指定就 403/连不上 |

### 审查视角（会炸的点）

1. `except Exception: pass` 吞掉了日志初始化失败。**日志起不来时你什么都看不到**，包括"为什么日志起不来"。生产上应至少写一份 `stderr` 兜底或系统事件日志。
2 `open(...)` 的文件对象 `f` 没有保存引用，靠 dup2 复制了 fd 后原对象被 GC 回收——Linux 上没问题（fd 已复制），Windows 上若 GC 时关闭原句柄可能让 1/2 变成无效句柄。当前能跑是因为 `f` 在函数局部一直活到函数返回，且 CPython 引用计数在这里的回收时机恰好晚于 dup2。**这是"能跑但依赖实现细节"的典型**。
3. 硬编码 `D:/FRIDAY` 作为默认值。机器没有 D 盘时 `mkdir(parents=True)` 会抛异常 → 被 `except` 吞掉 → **进程无日志启动**，出问题只能靠猜。

## 2. 连接管理与 WS 端点（`server.py` 24–80、477–507）

```python
class ConnectionManager:
    def __init__(self):
        self.active_connections: list[WebSocket] = []

    async def connect(self, websocket: WebSocket):
        await websocket.accept()
        self.active_connections.append(websocket)

    def disconnect(self, websocket: WebSocket):
        if websocket in self.active_connections:
            self.active_connections.remove(websocket)

    async def broadcast(self, message: dict):
        raw = json.dumps(message, ensure_ascii=False)
        for connection in self.active_connections:
            try:
                await connection.send_text(raw)
            except Exception:
                pass
```


### 逐段解析

- **单连接串行**：`while True: receive → handle`。同一条连接上第二个 `chat.send` 必须等第一个处理完。前端靠 `client_msg_id` 去重，不靠并发。
- **`broadcast` 串行 `await`**：一个慢连接会拖住所有广播（包括桌宠）。5 个前端就是 5 次串行网络写。
- **异常分两层**：内层捕获业务异常并回 `{"type":"error"}`，外层捕获断连。这是对的：一个坏事件不应该踢掉整条连接。

### 审查视角

1. **无背压**：`broadcast` 没有队列、没有超时。某前端卡住（比如浏览器标签被挂起）→ `send_text` 挂起 → 整轮对话的后续广播全卡。
2. **无心跳**：反代层（根 `server.py`）设了 `ping_interval=30`，但后端自己不 ping。中间设备掐断空闲连接时，`active_connections` 会留下僵尸，`broadcast` 每次都白等一个异常。
3. **断连不清理**：`broadcast` 里 `except: pass` 不会 `disconnect`，僵尸连接永远留着。正确做法是捕获后在列表里移除。
4. `json.loads(data)` 没有 try。客户端发非 JSON（比如浏览器扩展探测）会抛 `JSONDecodeError`，落到外层 `except Exception`，**直接断开整条连接**。

## 3. 原子写：`_safe_write_json`（`server.py` 390–423）

```python
def _safe_write_json(filepath, data: dict, retries: int = 5):
    """原子写入JSON文件 — 写临时文件后 os.replace，避免 Windows 文件锁问题

    ★ 不要用 tempfile.NamedTemporaryFile：Python 3.12 的 tempfile.TMP_MAX 是 2^31，
    某些云盘/虚拟盘的过滤驱动对 O_EXCL 创建持续返回"已存在"，会让它在那儿无限重试，
    把进程烧到 100% CPU 并焊死 asyncio 事件循环。
    """
    import os as _os
    import time as _time
    import uuid as _uuid
    filepath = Path(filepath)
    filepath.parent.mkdir(parents=True, exist_ok=True)
    payload = json.dumps(data, ensure_ascii=False, indent=2)
    last_err = None
    with _json_io_lock:
        for attempt in range(retries):
            tmp_name = f"{filepath}.{_uuid.uuid4().hex[:8]}.tmp"
            try:
                with open(tmp_name, 'w', encoding='utf-8') as f:
                    f.write(payload)
                _os.replace(tmp_name, str(filepath))
                return
            except Exception as e:
                last_err = e
                try:
                    _os.unlink(tmp_name)
                except Exception:
                    pass
                if attempt < retries - 1:
                    _time.sleep(min(1.0, 0.1 * (2 ** attempt)))
    logger.warning(f"Atomic write failed after {retries} retries: {filepath} - {last_err}")
    raise last_err
```

### 为什么这么写（这段注释本身就是一次事故复盘）

- `tempfile.NamedTemporaryFile` 在异常云盘上会**无限重试**创建临时文件，把 CPU 打满并堵死事件循环。作者改成 uuid 文件名 + 有限次重试。
- `os.replace` 在同一分区上是原子的（Windows 亦然），所以读方永远看到完整文件。
- `_json_io_lock` 是进程内互斥，防多协程/线程同时写。

### 审查视角（这段是全项目最值得挑的样本）

1. **在事件循环线程里 `time.sleep`**。`_safe_write_json` 被 async 路由直接调用时，`_time.sleep(0.1~0.8)` 会**阻塞整个 asyncio loop**。指数退避总时长最坏 1.5 秒，这 1.5 秒内所有 WS 心跳、所有对话都停摆。正确做法是 `asyncio.sleep`（但这就得改成 async 函数）或丢到线程池。
2. **`raise last_err` 可能是 `None`**。当 `retries=0` 时循环不执行，`last_err` 为 `None`，`raise None` 抛 `TypeError`，把"写失败"变成"类型错误"，日志完全误导。
3. **`filepath.parent.mkdir` 在锁外**。两个协程同时 mkdir 同一目录，Windows 上偶发 `FileExistsError`（`exist_ok=True` 应该覆盖，但过滤驱动不一定）。
4. **锁是 `threading.Lock`，不是 `asyncio.Lock`**。在 async 函数里 `with lock` 会**阻塞事件循环等待**；如果持锁的是另一个线程且它 sleep 了，事件循环就死等到锁释放。这是"用线程锁保护异步临界区"的经典错误。
5. **`json.dumps(data)` 在锁外**。大对象序列化可能几百毫秒，两个请求会重复序列化同一份数据（CPU 浪费，但不影响正确性）。

### 审查视角

1. ~~**`len(history) % 5 == 0` 在满 500 条后恒为真**~~【已修复 2026-11-11】。改前：前 500 条里每 5 条触发一次（100 次），之后长度恒为 500 → `500 % 5 == 0` 恒真 → **每条消息都触发一次 Viking 写入**。1000 条消息下：旧 600 次 vs 新 200 次。修法：独立计数器 `_viking_sync_counter`，且快照在锁内取。

## 6. 解析器一：`_parse_when`（2841–2942）

```python
def _parse_when(raw: str) -> Optional[float]:
    now = datetime.now()
    # 1) 相对量
    m = re.search(r"(\d+(?:\.\d+)?)\s*(?:天|日)\s*(?:之后|以后|后)", raw)
    if m:
        return (now + timedelta(days=float(m.group(1)))).timestamp()
    m = re.search(r"(\d+(?:\.\d+)?)\s*(?:个)?(?:小时|钟头)\s*(?:之后|以后|后)", raw)
    if m:
        return (now + timedelta(hours=float(m.group(1)))).timestamp()

    base: Optional[datetime] = None
    if "大后天" in raw:
        base = now + timedelta(days=3)
    elif "后天" in raw:
        base = now + timedelta(days=2)
    elif "明天" in raw:
        base = now + timedelta(days=1)
    elif "今天" in raw or "今晚" in raw:
        base = now

    # 2) 周几 / 下周几
    m = re.search(r"(下)?(?:周|星期)([一二三四五六日天])", raw)
    if m:
        target = _WEEKDAY[m.group(2)]
        days_ahead = (7 - now.weekday()) + target if m.group(1) else (target - now.weekday()) % 7
        base = (now + timedelta(days=days_ahead)).replace(hour=9, minute=0, second=0, microsecond=0)
    ...
    # 4) 具体钟点
    if got_clock:
        if ("下午" in raw or "晚上" in raw or "今晚" in raw or "傍晚" in raw) and hh < 12:
            hh += 12
        ...
    dt = base.replace(hour=hh, minute=mm, second=0, microsecond=0)
    if dt.timestamp() <= now.timestamp():
        dt += timedelta(days=1)
    return dt.timestamp()
```

### 解析顺序（有依赖，不能调换）

相对量 → 日偏移 → 周X → 月日 → N号 → 钟点 → **过期顺延**。

### 边界清单（每条都对应一次真实误判）

| 输入 | 结果 | 说明 |
|---|---|---|
| `3天后提醒我` | now+3d（**保留当前时刻**） | 相对量分支直接返回，不走"默认 9:00" |
| `明天提醒我` | 明天 09:00 | base 拿到，无钟点 → 默认 9 点 |
| `今晚提醒我` | 今天 20:00 | `今晚` 同时进 base 和 ampm 判断 |
| `明天下午三点` | 明天 15:00 | `下午` + `hh<12` → +12 |
| `周三` 今天是周四 | 下周三 09:00 | `(target - weekday) % 7` 保证向后 |
| `下周三` 今天是周四 | 下下周 09:00 | `(7 - weekday) + target`，语义上"下周三"常被理解为下周内 |
| `20号` 今天 25 号 | 下月 20 日 09:00 | `day < now.day` 顺延 |
| `2月30日` | `None` | `replace` 抛 `ValueError` 被捕获 |
| `三点`（现在是下午 4 点） | 明天 03:00 | 已过期 → +1 天；但没说"凌晨"，用户可能想要 15:00 |
| `下午三点`（现在 16 点） | 明天 15:00 | 同上 |
| `今晚提醒我`（现在 20:43） | 今天 **20:00** | 2026-11-11 修复：无钟点分支补 `mm = 0`；修复前是 20:43 |

### 审查视角

1. **"下个月/过几天/这两天"完全不认**。返回 `None` → `_parse_reminder` 里 `due_at=None` → 只 `pin` 不到点。用户说"下个月提醒我交房租"，系统永远不会提醒。
2. **无钟点分支没有重置分钟**【已修复 2026-11-11】：`今晚提醒我` 在 20:43 说，修复前得到 20:43 而不是 20:00。修法：`else:` 分支补 `mm = 0`。同轮还补了 `N 分钟后` 与"只说时段不给日期→按今天算"两个缺口。
3. **`三点` 的凌晨/下午歧义**。中文口语"三点"在下午场景下极少指凌晨 3 点，代码按"已过就顺延"给出明天凌晨，是**逻辑自洽但业务错误**。
4. **`今晚` 在 21:00 说** → base 今天、hh 20 → 已过期 → 明天 20:00。用户要的是"今晚"（已过，应该说"来不及了"），系统默默改成明晚。
5. **`周五` 与 `星期五` 的 `_WEEKDAY` 映射依赖字典**，`天/日` 两个别名必须都在，漏一个就 `KeyError`（当前被 `_parse_reminder` 的 try 吞掉，表现为"提醒没反应"）。
6. **无时区概念**：全部 `datetime.now()` 本地时间。跨时区/夏令时（国内没有）暂时安全。

## 7. 解析器二：`_parse_reminder`（2981–3005）

```python
def _parse_reminder(text: str) -> Optional[Dict[str, Any]]:
    raw = (text or "").strip()
    if not raw or not any(k in raw for k in _REMIND_TRIGGER):
        return None
    # 反问句不算（「你还记得吗」「记不记得」）
    if re.search(r"记(得|不记得)[^，。！？]{0,6}[吗么？?]", raw):
        return None
    has_time = bool(
        re.search(r"\d+\s*(?:天|日|小时|钟头)", raw)
        or re.search(r"(?:周|星期)[一二三四五六日天]", raw)
        or re.search(r"\d{1,2}\s*月\s*\d{1,2}", raw)
        or any(k in raw for k in _REMIND_DAYS)
    )
    imperative = any(k in raw for k in
                     ("提醒我", "提醒一下", "提醒下我", "帮我记", "记住",
                      "记得帮我", "别忘了", "别忘", "到时候提醒"))
    if not (imperative or (has_time and "提醒" in raw)):
        return None
    if raw.rstrip().endswith(("的", "吗", "？", "?")) and not has_time:
        return None
    due_at = _parse_when(raw)
    days = round((due_at - time.time()) / 86400.0, 1) if due_at else None
    return {"text": raw[:200], "due_at": due_at, "days": days}
```

### 判定树

```
有触发词? ──否→ 不记
   │是
反问句? ──是→ 不记（「你还记得吗」）
   │否
有祈使词(提醒我/帮我记/别忘了…)? ──是→ 记
   │否
有时间 且 含"提醒"? ──是→ 记
   │否
不问句 ──→ 记（pin 不到点）
```

### 审查视角

1. **`记住` 太宽**。"记住，我不吃辣" 会被当成提醒钉住（`due_at=None`），永远占一个 pin 名额。语义上这该进 `memory` 而不是 `pin`。
2. **`毕竟我记得…`** 这类陈述句如果带"记住"二字会被误判。当前靠 `imperative` 精确词表降低误伤，但 `记住` 本身就在表里。
3. **`text` 截断到 200 字**，但存的是**整句原话**（含"提醒我"）。注入时模型看到"10天后提醒我交报告（11-21 09:00 提醒）"，读起来重复。应该在存之前剥掉指令部分。
4. **`days` 用了 `time.time()` 而不是 `datetime.now().timestamp()`**。两者几乎相同，但混用两个时间源在跨模块比较时会有毫秒级误差，不影响业务。

## 8. 解析器三：`_ov_label`（2945–2965）

```python
def _ov_label(uri: str) -> str:
    u = uri or ""
    m = re.search(r"/tfgr/(\d{4}-\d{2}-\d{2})\.md$", u)
    if m:
        return f"[{m.group(1)[5:]} 当天汇总]"
    m = re.search(r"/mem/([^/]+)\.md$", u)
    if m:
        try:
            from brain.tfgr import get_tfgr
            e = get_tfgr().get(m.group(1))
            if e:
                day = datetime.fromtimestamp(e.ts).strftime("%m-%d")
                src = "他让记" if e.kind == "memory" else "我推断"
                return f"[{day} {src}]"
        except Exception:
            pass
    return "[旧记录]"
```

**为什么需要它**：Viking 返回的是一段裸文本 + 一个 `viking://...` URI。模型看到"他在调 TFGR 的图"无法判断这是今天的还是两周前的、是自己推的还是用户说的。这个函数把 URI 翻成 `[11-03 我推断]` 这种标签。

### 审查视角

1. **URI 格式是硬编码假设**。Viking 升级改了路径规则（比如加了租户前缀），所有命中都退化成 `[旧记录]`，静默失去时间信息——**不报错，只是变差**。
2. `get(...)` 是 O(n) 线性扫描 800+ 事件，在对话热路径里每条 OV 命中都扫一遍（最多 6 次）。
3. `[旧记录]` 兜底把"解析失败"和"真的是很旧的记录"混为一谈。

## 9. 解析器四：`_reply_mentions`（2968–2978）

```python
def _reply_mentions(reply: str, text: str) -> bool:
    r = (reply or "").lower()
    target = {c for c in (text or "") if "\u4e00" <= c <= "\u9fff"}
    if not r or not target:
        return False
    return sum(1 for c in target if c in r) / len(target) >= 0.4
```

**用途**：判断"这条提醒是否真的说出口了"。提醒被注入 prompt ≠ 用户听到了，模型可能顺口答别的。

### 审查视角

1. **40% 汉字重合**是个很松的阈值。提醒"明天交报告"（5 个字：明天交报告），回复里出现"明天""报告"就是 4/5=0.8 → 误判为已提醒。用户可能只是聊到明天天气。
2. **基数是 `set`（去重字符）**。同字重复的提醒（"报告报告"）基数变小，更容易误判。
3. 英文/数字提醒（"call John"）没有汉字，`target` 为空 → 永远返回 False → **英文提醒永远不会被标记完成**，每轮重复注入。

## 10. 解析器五：钩子 `parse_hook_specs`（`brain/mind.py`）

模型可以在回复末尾写：

```
<<after=120 note=过两分钟问问进度>>
<<idle=600 note=用户很久没动了>>
<<on=phone.boot note=手机开机了>>
```

`parse_hook_specs(markers)` 把这些解析成 `HookSpec(kind, delay, match, note, raw)`，再由 `Mind.add_hook` 落库。

### 审查视角

1. **模型可以写任意 `on=` 事件名**，包括不存在的事件 → 钩子永远不触发，静默泄漏（内存里越积越多）。
2. **`after` 无上限**。模型写 `<<after=99999999>>` 就是一个 3 年后的定时器；`_next_timeout` 若据此 sleep 会溢出或长期占位。
3. **钩子不落盘**（视实现），进程重启全丢。用户"过两分钟问我"在重启后就没了。
