# FRIDAY Plus 问题清单（风险台账）

> 生成日期：2026-11-11
> 用法：**先自己判断等级，再看我的**。等级口径：
> - **P0**：现在就能让服务不可用/数据损坏/被任意执行
> - **P1**：特定条件必现，或安全边界明显缺失
> - **P2**：会持续制造隐性错误（性能/一致性/可维护性）
> - **P3**：工程卫生，影响迭代速度
> 位置写法：`文件:行号`（按当前代码核对）。"未确认"的地方我会标出来。

## A. 安全与边界（6 条）

### A1 P1｜任意代码执行入口是敞开的
- **位置**：`api/server.py:2115` `POST /api/workspace/execute`；`:1605` WS `workspace.execute`
- **现象**：请求体 `content` 原样交给 `brain/workspace.py` 执行，返回 stdout/stderr。
- **触发**：本机任意进程 / 浏览器页面（配合 A2）POST 一段 Python。
- **后果**：等于把当前用户权限交给调用方。
- **判断**：这是**产品定位决定的**（本地单用户、AI 要跑代码），不是"忘了鉴权"。但必须在文档和面试里**主动讲清假设**，否则就是漏洞。
- **修法（上多用户/联网前必须做）**：127.0.0.1 绑定已是最低限度；再加 `token` 校验 + 执行白名单/沙箱 + 工作区根目录限制。
- **自查**：搜 `execute_script(`，看调用方有没有前置校验。

### A2 P1｜CORS 全开 + 无鉴权
- **位置**：`api/server.py:33-39`
- **现象**：`allow_origins=["*"]`、`allow_credentials=True`。
- **后果**：任意网页脚本可跨域访问本机后端（浏览器允许带凭证的 `*` 已被规范禁止，但无凭证请求仍成立），配合 A1 可远程触发执行。
- **修法**：白名单固定 `http://127.0.0.1:18090`；或干脆只允许同源。

### A3 P1｜密钥明文落盘
- **位置**：`backend/config/config.json`
- **现象**：模型/语音 key 直接写在 JSON（内容不在此复述）。
- **后果**：备份、截图、仓库误提交都会泄露。
- **修法**：改用环境变量或系统凭据库；至少把 `config.json` 放进 `.gitignore` 并做一次历史清理。

### A4 P2｜服务控制接口无保护
- **位置**：`api/server.py:535` `POST /api/service/stop`
- **现象**：任何本地请求都能把后端停掉（会触发 uvicorn 退出）。
- **修法**：加一次性 token；或只允许来自 18090 的反代请求。

### A5 P2｜OpenViking 本地服务无鉴权
- **位置**：`127.0.0.1:18095`（`scripts/start_openviking.ps1`）
- **现象**：写入/检索接口不校验调用方，`X-OpenViking-Account/User` 只是标识。
- **后果**：本机任意进程可读写记忆库。
- **修法**：同 A1，属于"本机可信"假设的一部分；联网前必须加认证。

### A6 P2｜日志可能包含对话原文与路径
- **位置**：`brain/memory.py`、`api/server.py` 多处 `logger.info(f"...{content[:40]}")`
- **后果**：日志文件被分享/截图时泄露隐私。
- **修法**：敏感字段脱敏；日志默认只记长度/哈希，不记原文。

## B. 稳定性（9 条）

### B1 P1｜持锁睡觉：磁盘异常时全进程停 1.5 秒
- **位置**：`api/server.py:390-423` `_safe_write_json`
- **现象**：`with _json_io_lock:` 内部 `_time.sleep(0.1/0.2/0.4/0.8)`。
- **触发**：Windows 文件锁 / 云盘过滤驱动 / 杀软占用。
- **后果**：调用方在 asyncio 事件循环上 → 所有 HTTP/WS（含语音流）一起停。
- **修法**：只把 `os.replace` 放进锁；重试与 sleep 放锁外；或整体改 async。
- **自查**：`with .*lock:` 里搜 `sleep|open|requests|httpx`。

### B2 P1｜同步函数里 `create_task`
- **位置**：`api/server.py:440-454` `_save_chat_message`（普通 `def`）
- **现象**：第 454 行 `asyncio.create_task(...)`。
- **触发**：从线程/执行器调用 `_save_chat_message`。
- **后果**：`RuntimeError: no running event loop`，且外层多为 `except`，静默失效。
- **修法**：改 `async def`；或 `try: loop = asyncio.get_running_loop()` 失败则退回同步写。
- **自查**：`create_task` 所在函数的签名是不是 `async def`。

### B3 P1｜节流在满 500 条后失效
- **位置**：`api/server.py:447-454`
- **现象**：`history = history[-500:]` 之后 `if len(history) % 5 == 0`。500 % 5 = 0。
- **后果**：聊天记录满 500 后，**每条消息**都触发一次 Viking 同步（设计是 1/5），调用量 5 倍。
- **修法**：用独立计数器（持久化或模块级），不要从被截断的集合长度反推。

### B4 P1｜`raise last_err` 可能是 `None`
- **位置**：`api/server.py:423`
- **现象**：`retries=0` 时循环不执行，`last_err=None` → `raise None` → `TypeError`。
- **后果**：报错与真实原因无关；调试时会被误导。
- **修法**：`if last_err is None: raise RuntimeError(f"write failed: {filepath}")`。

### B5 P2｜TFGR 在事件循环里同步落盘
- **位置**：`brain/tfgr.py` `_persist`（每 2MB 轮转/每次写入），被 `remember` / `record` / `penalize_recent` 调用
- **现象**：整份 JSONL `write_text`，同步 IO。
- **后果**：事件多时（当前 780+ 条）每次写几 MB，卡住对话。
- **修法**：增量 append（本来就有 `_append`）+ 定期压缩；或丢到线程池。

### B6 P2｜广播无背压
- **位置**：`api/server.py:46-71` `ConnectionManager.broadcast`
- **现象**：顺序 `await` 每个连接；慢客户端（或断网重连）会拖住整轮广播。
- **后果**：一个卡住的 WS 让所有人收不到消息。
- **修法**：`asyncio.gather(..., return_exceptions=True)` + 单连接队列/超时踢出。

### B7 P2｜WS 没有心跳/空闲回收
- **位置**：`api/server.py:478-500`
- **现象**：只依赖底层 TCP；半开连接可能长期占着 `active_connections`。
- **修法**：定时 ping / 记录 `last_seen`，超时 `disconnect`。

### B8 P3｜日志无轮转
- **位置**：`backend/run_server.py:48-58`（`open(..., "a")`）
- **后果**：`plus_backend.log` 无限增长（当前已多次出现编码混杂的历史段）。
- **修法**：`logging.handlers.RotatingFileHandler` 或启动时按大小切分。

### B9 P3｜`wsproto` 是兼容性补丁
- **位置**：`backend/run_server.py` `uvicorn.run(ws="wsproto")`
- **现象**：依赖 websockets 旧版本握手。
- **后果**：升级任一依赖可能再次 400/握手失败。
- **修法**：锁版本 + 启动自检（WS 握手 smoke test）。

## C. 记忆与对话（13 条）

### C1 P1｜`digest` 每次全表扫描
- **位置**：`brain/tfgr.py:590`
- **现象**：每轮对话遍历全部事件（当前 780+，上限 2000），并对推断做 `SequenceMatcher`。
- **后果**：对话首字延迟随使用时间线性上升。
- **修法**：维护 `due` 小顶堆 + `USER_KINDS`/`pin` 索引；推断只扫最近 N 天。

### C2 P1｜`touch`/`last_inject` 在锁外改 `meta`
- **位置**：`brain/tfgr.py:610-616`
- **现象**：`digest` 在 `with self._lock` 外直接写 `e.meta["last_inject"]`；`touch` 另取锁。
- **后果**：与 `prune`/`consolidate`/`_persist` 并发时状态不一致（尤其未来加线程/多 worker）。
- **修法**：把 picked 的 meta 更新放进同一次锁内批量提交。

### C3 P1｜负反馈可能误伤
- **位置**：`brain/tfgr.py:463-496` `penalize_recent`
- **现象**：命中"你记错了/我没说过"就罚"最近注入的前 2 条"；字面重合 ≥0.3 也会罚。
- **后果**：用户否定的是别的事，记忆被无故降权。
- **修法**：先让模型/规则确认"否定对象"；或只在回复文本与记忆有交集时罚；加"误罚可撤销"入口。

### C4 P2｜"下个月/过几天/这两天"只钉住不到点
- **位置**：`_REMIND_DAYS`（2834 附近）vs `_parse_when`（2841）
- **现象**：这三个词让 `has_time=True`，但 `_parse_when` 没有对应分支 → `due_at=None`。
- **后果**：用户以为设了提醒，实际永远不会被唤醒。
- **修法**：补 `下个月`（当月+1，日不变，越界取月末）、`过几天`（+3）、`这两天`（+1）。

### C5 P2｜提醒识别会误判祈使句
- **位置**：`_parse_reminder:2981`
- **现象**：`"记住这个函数名"` / `"记得这个坑"` 命中"记住/记得"。
- **后果**：往长期记忆写垃圾，挤占注入预算。
- **修法**：要求"提醒我/帮我记/别忘"等明确祈使；"记住"后若接"这个/那个"改为普通对话。

### C6 P2｜提醒完成判定过宽
- **位置**：`_reply_mentions:2968`
- **现象**：汉字集合重合 ≥40% 即视为"已提醒"。
- **后果**：短提醒（"交报告"）回复里出现两个字就被标记完成，用户可能没真听到。
- **修法**：要求连续子串命中（如 2-gram 覆盖 ≥50%）+ 只在回复包含"提醒/记得/该"等语义词时生效。

### C7 P2｜`memory_context` 是死链路
- **位置**：`api/server.py:852-913`
- **现象**：`MemoryManager.search_memories` 只做 `query_lower in text`，且 `_memories_cache` 常为空（Viking 关闭）。
- **后果**：每轮白跑一次检索 + 一条 "NOTHING extracted" 日志；`【记忆】` 块几乎永远是空。
- **修法**：Viking 关闭时直接跳过；或改成语义检索（复用 OV）。

### C8 P2｜复读兜底会多一次模型调用
- **位置**：`api/server.py:1307-1322`
- **现象**：相似度 ≥0.9 时同步再调一次 `llm.chat` 重写。
- **后果**：偶发多 3–5 秒延迟；且流式已经把原文显示过，最终文本会"跳变"。
- **修法**：把重写改成"追加一句差异"（保留流式前缀），或把阈值提高到 0.95 并只对短回复生效。

### C9 P2｜身份边界只靠 prompt
- **位置**：`api/server.py:147-152`
- **现象**：5 条硬事实写在 system prompt。
- **后果**：长上下文/强指令下仍可能被冲淡；没有输出侧校验。
- **修法**：对"身份类问题"做意图识别，命中时用模板兜底（不交给模型自由发挥）。

### C10 P2｜`meta` 无 schema
- **位置**：`brain/tfgr.py` `TFEvent.meta`
- **现象**：`pin/due_at/done/done_at/done_note/last_hit/last_inject/negated` 全靠约定。
- **后果**：拼错 key 不报错，功能静默失效（例如写成 `last_injected`）。
- **修法**：定义常量或 TypedDict；读写统一走小函数。

### C11 P3｜按天 OV 文档全量覆盖
- **位置**：`brain/ov_memory.py:241-260`
- **现象**：当天任一事件变化 → 整篇 `tfgr/YYYY-MM-DD.md` 重写。
- **后果**：一天内多次写放大；OV 侧历史版本不可回溯。
- **修法**：按小时分片，或只追加不覆盖（append 模式）。

### C12 P3｜`consolidate` 的二次复杂度
- **位置**：`brain/tfgr.py:684`
- **现象**：每条与 `recent[-300:]` 做 `SequenceMatcher`。
- **后果**：最多 2000×300 次比较，整理一次可能秒级。
- **修法**：先按 kind + 时间桶分桶，再比对。

### C13 P2｜`no_response_count` 已成死计数
- **位置**：`core/state.py:194-205`，唯一自增在 `api/server.py:4025`（语音间隙续接）
- **现象**：Plus 不跑语音，计数永远 0；Mind 用的是自己的 `_ignored_streak`。
- **后果**：日志 `no_resp=0` 会误导判断；状态面板显示不准。
- **修法**：要么在 Mind 说话未被回应时也调 `increment_no_response`，要么删掉这个字段统一口径。

## D. 工程（9 条）

### D1 P1｜`server.py` 4,190 行
- **位置**：`backend/api/server.py`
- **现象**：100+ 端点、20 个 Pydantic 模型、对话/记忆/语音/机械臂全在一个文件；`handle_chat_send` 约 675 行。
- **后果**：任何改动都要读 4,000 行确认没碰别的状态。
- **修法（低风险拆分顺序）**：先拆 `routers/`（按域：chat/memory/workspace/voice/status），再拆 `services/`（历史、记忆、注入组装），最后拆 `handle_chat_send`。

### D2 P2｜函数内 `import`
- **位置**：`_safe_write_json` 里 `import os/time/uuid`；全项目大量方法级 import。
- **后果**：依赖关系藏在函数体里，循环依赖难以发现。
- **修法**：除"打断循环依赖"外一律提到顶部，并写注释说明。

### D3 P2｜硬编码本机路径/端口
- **位置**：`run_server.py`、`scripts/*.ps1`、`start_*.vbs`、`core/config.py`（`D:/FRIDAY`）
- **后果**：换机器/换用户直接启动失败。
- **修法**：统一 `Path(__file__)` + `FRIDAY_HOME`；脚本用相对路径。

### D4 P2｜没有测试
- **现状**：`backend/tests` 不存在，仓库里没有 `test_*.py`、没有 CI。
- **后果**：`_parse_when`、`digest` 这类纯函数明明最好测，却只能靠手测。
- **建议的最小测试集（半天能写完）**：
  1. `_parse_when` 的 12 条边界（见 `04_代码导读.md` 4.1）；
  2. `_parse_reminder` 的 8 条正反例；
  3. `digest` 的分层/预算/去重（用临时 `FRIDAY_HOME` 隔离数据）；
  4. `_too_similar` 的阈值回归。

### D5 P2｜前端源码暂时不能构建
- **位置**：`backend/frontend/src/`（17 文件，已从 sourcemap 还原）
- **缺失**：`types.ts`、`index.css`、`package.json`、`vite.config.ts`、`tsconfig`、`tailwind`、`index.html`
- **后果**：只能读、不能改；桌宠 UI 的迭代被卡住。
- **修法**：按源码 import 反推依赖（react/react-dom/zustand/lucide-react/tailwind），重建脚手架后跑一次 `npm run build` 对比产物。

### D6 P2｜两套前端并存
- **现象**：`ui/` 手写 4 页 + `backend/frontend` React 桌宠页，两套 UI、两套 WS 处理。
- **后果**：协议改一次要改两处；样式无法复用。
- **修法**：先统一 WS 封装（把事件表抽成一份 JS/TS），再决定长期保留哪套。

### D7 P3｜语音遗留代码仍在启动路径
- **位置**：`api/realtime_ws.py`（836 行）、`voice_chat_v2.py`（688）、`rtc_token.py`（160）、`brain/voice_bridge.py`（101）、`brain/realtime_dialog_tool.py`（631）
- **现状**：Plus 不建立语音会话，但路由（`/api/realtime/ws`）与引用都在。`api/bridge.py` 已在本轮删除。
- **判断**：这些不是死代码（`server.py` 有路由引它们），删了会改变 API 面。**保留**，但要在文档里写明"Plus 不启用语音"。
- **修法**：若要彻底清，先删 `server.py` 的 `/api/realtime/ws` 路由与 `send_tts` 工具，再删文件。

### D8 P3｜`subbrain_demo` 硬 import 阻挡清理【已解决】
- **原位置**：`brain/activity_timeline.py:1190,1224,1238,1246,1333`（`TFGRActivityBridge`）
- **本轮处理**：删除 `TFGRActivityBridge` 整个类（约 230 行）→ `subbrain_demo`/`state_core` 失去唯一硬 import → 两者已删除；`models`（5.9GB）/`checkpoints`（31MB）一并永久删除。
- **残留验证**：`grep -rn "subbrain\|state_core" backend/` 无命中。

### D9 P3｜仓库混杂
- **现象**：根目录同时有职业文档、比赛材料、脚本生成器、模型素材（`models` 5.9GB、`DeepSeek免费公皮` 186MB）。
- **后果**：新人（或面试官）打开仓库不知道从哪看。
- **建议**：运行链路保留；素材移到 `_assets/`；文档移到 `docs/`；大模型/checkpoint 不进仓库。
