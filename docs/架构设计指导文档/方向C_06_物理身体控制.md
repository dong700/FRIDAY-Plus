## 1. 摘要

Lucy 是一个**具身**对话机器人：它拥有物理本体（头、面、臂、底盘），需要被驱动起来运动。在系统的三路径架构中，α 路径管"用户在等时的秒级响应"，β 路径管"副脑主动发起的可预计算调度"，γ 路径管"身体的毫秒级硬实时控制"。模块6（M6）就是 γ 路径的执行者。

M6 的核心职责有四项：

1. **硬实时控制环**：以 30–60Hz（每 tick 16–33ms）的频率循环执行"读传感器 → 状态估计 → 运动规划 → 安全检查 → 写执行器"，绝不阻塞对话路径（α/β）。
2. **意图执行**：消费 M2 副脑异步下发的高级 `BodyIntent`（IDLE/LISTENING_POSE/SPEAKING_POSE/APPROACH_USER/WAVE/NOD/CARE_GESTURE/THINKING_POSE），自主映射为关节空间轨迹并执行，完成后回执。
3. **口型同步与表情**：接收 M4 TTS 音频特征（viseme/音量/基频），映射为嘴形参数；同时根据情绪/姿态生成面部 LED 或屏幕表情。
4. **安全兜底**：硬件急停按钮、关节限位、碰撞检测、IMU 倾倒检测、看门狗心跳（100ms 无心跳 → 紧急冻结）等多层保护，保证身体失控时第一时间停机。

M6 的设计哲学是**意图级抽象 + 本地自主 + 与主脑 API 彻底解耦**：M2 副脑只发"挥手""走向用户"这样的高级意图，绝不发关节角或舵机 PWM；轨迹规划、逆运动学、安全检查全部由 M6 在本地完成；M6 既不调用主脑 API，也不依赖主脑 API 可用性——主脑 API 是云端的、可能超时或断网的外部服务，M6 把它当作"可能消失的外部世界"对待，自身控制环完全自包含。这样 M2 不会被低层细节拖慢，M6 也不会被 M2 的决策节奏或主脑 API 的网络状态牵制——三者通过非阻塞的意图队列与独立的实时核解耦。

## 2. 模块定位（具身运动的实时控制层）

### 2.1 在三路径架构中的位置

```
┌────────────────────────────────────────────────────────────────┐
│  α 快速响应路径（秒级，用户在等）                                  │
│   ASR → M2 判定 → M3 调主脑 API 流式 → M4 TTS → 输出             │
│                          │                                      │
│                          │  M6 仅做并行身体动作启动              │
│                          ▼  （点头/注视，<100ms 启动，不阻塞 α）  │
├────────────────────────────────────────────────────────────────┤
│  β 主动发起路径（可预计算，副脑触发）                              │
│   M2 tick → 决策 → 预热主脑 API → 播放                            │
│        │                                                         │
│        └─► M2 发 BodyIntent → M6 执行（APPROACH/CARE/WAVE）       │
├────────────────────────────────────────────────────────────────┤
│  γ 身体实时控制路径（毫秒级，硬实时）       ◄── M6 在此            │
│   独立 RT 核，30-60Hz 控制环，禁迁移，最高优先级                  │
│   接收：M2 BodyIntent（异步）/ M4 音频特征（流）                  │
│   回报：BodyAck / SensorEvent                                    │
│   不依赖：主脑 API（云端 LLM 挂掉时 γ 路径完全不受影响）           │
└────────────────────────────────────────────────────────────────┘
```

**关键定位**：γ 路径是三条路径中唯一不与主脑 API 发生任何耦合的路径。α 路径调主脑 API 流式生成回复，β 路径调主脑 API 预生成/思考模式，γ 路径只与 M2（接收意图）和 M4（接收音频特征）耦合。这意味着主脑 API 故障（401/403/超时/网络断）时，α/β 路径会触发 L3/L7 降级，但 γ 路径的身体控制环照常运行——Lucy 仍能维持姿态、执行已下发的意图、保证安全。

### 2.2 与其他模块的边界

- **不与 M2 共享线程**：M2 在"对话核"上跑决策循环，M6 在"RT 核"上跑控制环，物理隔离（主文档 §9 部署拓扑）。
- **不依赖 M1**：M6 不直接读 UserState；用户状态变化经 M2 转译为 BodyIntent。
- **不依赖主脑 API**：M6 既不调用主脑 API（DeepSeek/OpenAI），也不依赖其可用性。主脑 API 挂掉或网络断时，M6 仍能维持基本姿态与安全——这是 γ 路径相对 α/β 的根本韧性优势。M6 把主脑 API 视为"可能消失的外部世界"，自身控制环完全自包含。
- **不依赖 M3**：M3 是主脑 API 调用与身份守卫层，M6 与 M3 无任何数据流耦合。
- **接收 M4 音频特征**：唯一的跨模块高频输入，专用于口型同步，独立通道。M4 音频断流时口型归零，身体控制不受影响。
- **不调用 M5**：M6 不发起工具调用；必要时通过 M2 间接调用（如查询导航地图）。

### 2.3 设计原则

1. **意图级接口**：M2 只发意图，M6 自主规划。M2 不发关节角、不发 PWM。
2. **本地闭环**：轨迹规划、IK、安全检查全部本地完成，不依赖网络、不依赖主脑 API。
3. **与主脑 API 彻底解耦**：主脑 API 不可用时身体正常运动；仅 SPEAKING_POSE 在无音频时退化为待机表情。
4. **安全优先**：任何不确定情况优先冻结。
5. **降级可用**：单关节失效、传感器失效、通讯断、主脑 API 断都能让身体进入可控状态而非失控。
6. **可观测**：每个 tick 输出结构化遥测，便于调试与安全审计。

## 3. 身体硬件抽象

M6 通过硬件抽象层（HAL）与物理本体解耦，使上层控制逻辑可在仿真器与真实本体间无缝切换。HAL 是 M6 与物理本体的唯一接口，也是 M6 不依赖任何外部服务（包括主脑 API）的工程基础——所有传感器读数与执行器写入都在本地总线完成。

### 3.1 关节模型（DOF 定义 / 关节限位 / 速度限制）

机器人本体的关节空间定义如下（典型配置）：

| 部位 | DOF 数 | 关节名 | 角度范围（deg） | 最大角速度（deg/s） |
|------|-------|--------|----------------|--------------------|
| 头部 | 3 | head_pitch（俯仰） | -30 ~ +20 | 120 |
|      |   | head_yaw（偏航）   | -45 ~ +45 | 120 |
|      |   | head_roll（翻滚）  | -20 ~ +20 | 90  |
| 面部 | — | mouth_open（开合度） | 0 ~ 1（归一化） | 10/s |
|      |   | eye_led_r / eye_led_l | RGB 值 | — |
|      |   | brow_l / brow_r | -1 ~ +1 | 5/s |
| 左臂 | 7 | l_shoulder_pitch | -60 ~ +120 | 120 |
|      |   | l_shoulder_roll  | -30 ~ +120 | 120 |
|      |   | l_shoulder_yaw   | -90 ~ +90  | 120 |
|      |   | l_elbow          | -10 ~ +130 | 150 |

**关节状态结构**：

```python
@dataclass
class JointState:
    name: str
    position_rad: float          # 当前角度（rad）
    velocity_rad_s: float        # 当前角速度
    torque_Nm: float             # 当前力矩（如支持）
    temperature_C: float         # 舵机/电机温度
    error_flags: int             # 0=正常；bit 位编码故障
```

### 3.2 传感器模型（IMU / 编码器 / 触觉）

| 传感器 | 采样率 | 数据 | 用途 |
|--------|--------|------|------|
| IMU（6轴） | 200Hz | 加速度（x/y/z, m/s²）+ 角速度（roll/pitch/yaw, rad/s） | 倾倒检测、姿态估计、运动平滑 |
| 关节编码器 | 与控制环同频 | 每个关节的位置/速度 | 闭环反馈 |
| 触觉皮肤 | 100Hz | 压力阈值二值/模拟量 | 碰撞感知、人机接触检测 |
| 超声/TOF | 30Hz | 前方距离（m） | 移动避障 |
| 摄像头（共享 M4） | 30Hz | RGB-D | 视觉避障/用户定位（M4 主用，M6 副用） |
| 麦克风（共享 M4） | — | — | M4 主用，M6 不直接读 |

**IMU 倾倒判据**：当加速度向量与重力方向的夹角 > 35° 持续 > 50ms，判定为"倾倒预警"；> 60° 持续 > 30ms 判定为"已倾倒"，立即冻结所有关节并上报 `SensorEvent(severity="critical")`。

### 3.3 执行器模型（总线舵机 / 步进电机 / 无刷电机 / LED 阵列）

| 执行器类型 | 部位 | 控制方式 | 死区/响应 |
|-----------|------|---------|----------|
| 总线舵机 | 头/臂/手腕 | 位置指令（角度+速度） | 响应 < 5ms |
| 步进电机 | 底盘 | 速度指令（m/s） | 加速度限制 ±0.5 m/s² |
| 无刷电机 | 高负载关节（可选） | 力矩指令 | 电流环 1kHz |
| LED 阵列 | 面部表情 | RGB 值（每像素） | < 10ms |
| 简易屏幕（可选） | 面部表情 | 帧缓冲（30Hz） | 与控制环同步 |

**执行器写入原则**：
- 每个写指令都带超时戳，过期指令丢弃（防止网络抖动导致旧指令堆积）。
- 舵机/电机温度超阈值（如 70°C）时，该关节降速到 30%，并上报 warning。
- 底盘电机永远受加速度限制约束，禁止阶跃。
- 执行器总线是本地总线（CAN/RS485/总线舵机协议），不经过网络，不依赖主脑 API。

### 3.4 硬件抽象层（HAL）接口

HAL 是 M6 与物理本体的唯一接口。上层只看到统一的 `HAL` 接口，下层对接真实硬件或仿真器。

```python
class HAL(Protocol):
    # 读
    def read_joint_states(self) -> List[JointState]: ...
    def read_imu(self) -> IMUReading: ...
    def read_tactile(self) -> TactileReading: ...
    def read_distance(self) -> List[float]: ...   # 多向距离
    # 写
    def write_joint_targets(self, targets: List[JointTarget]) -> None: ...
    def write_face(self, expression: FaceFrame) -> None: ...
    def write_base_velocity(self, v: float, omega: float) -> None: ...
    # 紧急
    def emergency_stop(self) -> None: ...           # 硬切断所有执行器
    def release_estop(self) -> bool: ...            # 软释放（需人工确认）

# 实现三态：
# - HALHardware：对接真实硬件（总线舵机 + IMU + 编码器 + 触觉 + TOF）
# - HALSimulator：仿真（用于控制算法开发与回归测试，无真实硬件）
# - HALPlayback：回放日志（用于复现 bug，从录制好的传感器流重放）
```

HAL 实现必须保证 `read_*` 与 `write_*` 是非阻塞且确定性时延（<2ms），否则破坏控制环周期。三态 HAL 让控制逻辑可先在仿真器上验证再上真机，降低具身调试的风险与成本。

## 4. 实时控制环（γ 路径核心）

控制环是 M6 的心脏。每个 tick 必须在预算时间内完成五步：传感器读取 → 状态估计 → 运动规划 → 安全检查 → 执行器写入。这五步全部在本地 RT 核完成，不调用任何外部服务（包括主脑 API）。

### 4.1 控制环结构（30–60Hz，5 步预算分配）

```
[M6 控制环] @ 30Hz（默认，每 tick 33.33ms）
├─ t0         周期开始（由硬件定时器唤醒 RT 线程）
├─ t0..t0+2ms   ① 读传感器（IMU / 关节编码器 / 触觉 / 距离）
├─ t0+2..t0+4ms ② 状态估计（卡尔曼滤波融合关节+IMU）
├─ t0+4..t0+14ms ③ 运动规划（IK / 动作插值 / 轨迹生成 / 导航避障）
├─ t0+14..t0+15ms ④ 安全检查（限位 / 碰撞 / 倾倒 / 急停）
├─ t0+15..t0+17ms ⑤ 写执行器（关节目标 / 面部 / 底盘）
├─ t0+17..t0+18ms 心跳发送（共享内存 + UDP）
├─ t0+18..t0+33ms 空闲（等待下一周期；可做遥测/日志）
└─ t0+33.33ms 下一周期
```

预算分配理由：
- ①②⑤ 是确定性 IO，时延固定（<2ms 各）。
- ③ 是最不确定的，IK 求解与动作插值可能耗时 5–10ms，留 10ms 预算。导航避障（APPROACH_USER 时）也在此预算内完成。
- ④ 必须极快（<1ms），因为它是安全闸门，越快停机越安全。
- 心跳紧贴写执行器之后，保证"我刚写完还活着"这个信号是最新的。

**频率自适应**：默认 30Hz。当 ③ 连续 10 个 tick 实测 < 5ms 且 CPU 占用 < 60%，自动切 60Hz 以获得更平滑运动；反之降回 30Hz。

### 4.2 传感器读取与状态估计（卡尔曼滤波融合关节 + IMU）

**原始读数存在噪声**：编码器有量化误差，IMU 有零偏与漂移，触觉有抖动。直接用原始值做控制会导致抖动。M6 用卡尔曼滤波融合多源信息得到平滑且无延迟的状态估计。

**状态向量**（以单关节为例，可推广到全关节空间）：

```
x = [q, q_dot, q_ddot]^T
其中 q = 关节角度，q_dot = 角速度，q_ddot = 角加速度
```

**运动模型**（匀加速度模型）：

```
x_{k+1} = A·x_k + B·u_k + w_k
A = [1  dt  0.5·dt²]
    [0  1   dt   ]
    [0  0   1    ]
B = 0（M6 用无控制项模型，控制由目标轨迹体现）
u_k = 0
```

**观测模型**：

```
z_k = [q_enc, q_dot_imu]^T = H·x_k + v_k
H = [1 0 0]
    [0 1 0]
```

`q_enc` 来自关节编码器（位置准但速度噪声大），`q_dot_imu` 来自 IMU 角速度（平滑但有零偏）。两者融合后得到既准又平滑的估计。

**实现要点**：
- 滤波器参数（Q 过程噪声、R 观测噪声）按关节标定，存配置文件。
- IMU 零偏在上电时静态校准 2 秒。
- 当编码器与 IMU 差异 > 阈值（如 5°）持续 > 100ms，判定传感器异常，进入降级（§8.2）。

### 4.3 运动规划（逆运动学 DLS / 动作插值 jerk-limited / 预设动作库 / 导航避障）

运动规划把"目标姿态/轨迹"转换为关节空间目标角度。分四类：

**A. 预设动作（动作库）**：挥手、点头、关怀手势等已编排好的关键帧序列。规划就是按时间插值。

```python
def plan_preset_motion(motion: PresetMotion, t_now: float) -> JointTrajectoryPoint:
    # motion.keyframes: List[(t_rel, JointPose)]
    # 找到当前时间所在的两个关键帧，做三次样条插值
    kf_prev, kf_next = find_segment(motion.keyframes, t_now - motion.start_t)
    alpha = (t_now - motion.start_t - kf_prev.t) / (kf_next.t - kf_prev.t)
    alpha = clamp(ease_in_out(alpha), 0, 1)
    pose = lerp_pose(kf_prev.pose, kf_next.pose, alpha)
    return JointTrajectoryPoint(pose, dt=control_dt)
```

**B. 实时 IK 求解（DLS 阻尼最小二乘）**：如需把笛卡尔目标转为关节角（精细操作场景），用 DLS 逆运动学。

```python
def solve_ik(target_pose: CartesianPose, arm: str) -> JointPose:
    # DLS（Damped Least Squares）逆运动学
    # J = 雅可比（数值差分），lambda = 阻尼系数
    # 迭代 q_{k+1} = q_k + J^T·(J·J^T + lambda²·I)^-1 · (target - FK(q_k))
    for _ in range(max_iter=10):
        err = target_pose - forward_kinematics(q)
        if norm(err) < tol: break
        J = numerical_jacobian(q)
        dq = J.T @ inv(J @ J.T + lambda²·I) @ err
        q = q + dq
    return q
```

**D. 导航避障（APPROACH_USER 时）**：底盘路径规划用反应式势场法，无全局 SLAM（机器人工作空间小）。

```python
def plan_approach(user_xy: Tuple[float,float], state: RobotState) -> BaseCmd:
    # 简单势场避障：目标吸引 + 障碍排斥
    goal_vec = np.array(user_xy) - np.array(state.base_xy)
    dist = np.linalg.norm(goal_vec)
    if dist < APPROACH_THRESHOLD:  # 0.6m
        return BaseCmd(0.0, 0.0)  # 已到，停
    # 速度按距离衰减（接近时减速）
    v = min(MAX_V * (dist / 1.0), MAX_V)
    # 朝向目标
    target_theta = math.atan2(goal_vec[1], goal_vec[0])
    theta_err = wrap_angle(target_theta - state.base_theta)
    omega = clip(theta_err * 2.0, -MAX_OMEGA, MAX_OMEGA)
    # 避障：用前方距离传感器
    if state.min_front_distance < 0.3:
        v *= 0.2  # 大幅减速
        if state.min_left_distance > state.min_right_distance:
            omega += 0.5  # 左转绕
        else:
            omega -= 0.5
    if state.min_front_distance < 0.15:
        v = 0.0  # 停
    return BaseCmd(v, omega)
```

**底盘运动学（差速驱动）**：

```
v_left  = v - omega·L/2
v_right = v + omega·L/2
L = 轮距
```

底盘速度变化率限制 ±0.5 m/s²，防止急停导致本体前倾。

**避障策略分层**：
1. 远（> 0.5m）：正常导航
2. 近（0.3–0.5m）：减速
3. 极近（< 0.3m）：停止 + 上报 `SensorEvent("obstacle")`
4. 接触（触觉触发）：立即停 + 回报 M2

### 4.4 安全检查（关节限位 / 速度限制 / 自碰撞 / 外部碰撞 / 倾倒 / 急停）

安全检查是写执行器前的最后一道闸门。**任何一项不通过 → 这一 tick 不写新指令，按上一安全状态保持或触发冻结。**

```python
def safety_check(targets: List[JointTarget], state: RobotState) -> SafetyResult:
    # 1. 关节限位（软限位比硬限位内缩 2° 留余量）
    for t in targets:
        soft_lo, soft_hi = soft_limit(t.name)
        if not (soft_lo <= t.position <= soft_hi):
            return SafetyResult.fail(f"joint {t.name} out of soft limit: {t.position}")
    # 2. 速度限制
    for t in targets:
        if abs(t.velocity) > max_vel(t.name) * 1.05:
            return SafetyResult.fail(f"joint {t.name} over-speed")
    # 3. 自碰撞（用简化包围盒快速检测）
    if self_collision_check(targets):
        return SafetyResult.fail("self-collision detected")
    # 4. 外部碰撞（触觉+距离传感器）
    if state.tactile.any_pressed() and state.base_velocity > 0.1:
        return SafetyResult.fail("external contact while moving")
    if state.min_distance < 0.15 and state.base_velocity > 0.05:
        return SafetyResult.fail("obstacle too close")
    # 5. 倾倒
    if state.tilt_angle > 35:
        return SafetyResult.fail(f"tilt warning: {state.tilt_angle}")
    # 6. 急停按钮
    if state.estop_pressed:
        return SafetyResult.fail("E-Stop pressed")
    return SafetyResult.ok()
```

**碰撞检测的简化**：用球体/胶囊体包围盒表示身体各段，做 O(n²) 但 n 很小（<20）的成对距离检查。实测可在 0.3ms 内完成。

### 4.6 RT 线程与 CPU 亲和性（SCHED_FIFO / 禁迁移 / 内存预分配 / 看门狗）

```python
# Linux：用 SCHED_FIFO 实时调度 + CPU 亲和性绑定
import os, ctypes

def setup_rt_thread(cpu_id: int, priority: int = 80):
    # 设置 CPU 亲和性
    os.sched_setaffinity(0, {cpu_id})
    # 设置实时优先级（SCHED_FIFO）
    param = os.sched_param(priority)
    os.sched_setscheduler(0, os.SCHED_FIFO, param)
    # 锁定内存，避免页错误导致抖动
    ctypes.CDLL('libc.so.6').mlockall(3)  # MCL_CURRENT|MCL_FUTURE

# 主控制环（运行在 RT 线程内）
def control_loop(hal: HAL, intent_queue, audio_queue):
    setup_rt_thread(cpu_id=RT_CORE_ID, priority=80)
    next_wake = monotonic_now()
    while not shutdown_flag.is_set():
        next_wake += PERIOD_NS  # 33.33ms for 30Hz
        tick(hal, intent_queue, audio_queue)
        # 精确睡眠到下一个周期（clock_nanosleep，绝对时间）
        sleep_until_absolute(next_wake)
```

**关键约束**：
- 控制环线程**禁迁移**到其他 CPU 核（避免 cache 失效抖动）。
- 控制环内**禁止**：堆分配、IO 阻塞、Python GIL 持久持有（核心循环用 C 扩展或预分配缓冲）。
- 内存预分配：所有 tick 用到的缓冲区在启动时一次性分配，运行时不 `new`。
- 100ms 无心跳 → 外部看门狗（独立硬件或独立进程）触发紧急制动。
- 控制环内**禁止任何网络调用**——不调主脑 API、不调 M5 工具、不查云端地图，保证 γ 路径的时序确定性。

## 5. 意图执行引擎

### 5.1 BodyIntent 队列管理（M2 异步下发 / M6 非阻塞取最新）

M2 通过共享内存或本地 socket 把 `BodyIntent` 实例推入 M6 的意图队列。M6 在每个 tick 的"规划"阶段非阻塞地取队列最新意图。

```python
@dataclass
class IntentEnvelope:
    intent: BodyIntent
    intent_id: str            # 唯一 ID，用于回执
    priority: int             # 0=低 1=中 2=高（急停类）
    params: dict              # 参数（如 APPROACH_USER 的目标坐标）
    timestamp: float          # 发送时间戳（检测过期）
    ttl_ms: int = 2000        # 过期丢弃

class IntentQueue:
    def __init__(self, maxlen: int = 8):
        self._buf = collections.deque(maxlen=maxlen)
        self._lock = threading.Lock()
    def push(self, env: IntentEnvelope):
        if monotonic_now() - env.timestamp > env.ttl_ms / 1000.0:
            return  # 过期丢弃
        with self._lock:
            self._buf.append(env)
    def latest(self) -> Optional[IntentEnvelope]:
        # 非阻塞取最新（peek 不消费，由引擎决定是否消费）
        with self._lock:
            return self._buf[-1] if self._buf else None
    def clear(self):
        with self._lock:
            self._buf.clear()
```

**队列策略**：
- 队列上限 8 条，老的丢弃（防止 M2 卡顿后突然灌一堆旧意图）。
- 取最新而非 FIFO——意图是"覆盖式"语义，新意图通常代表更紧迫的目标。
- 过期意图（>ttl）在入队时即丢弃，不进入规划。

### 5.2 意图 → 轨迹映射

8 个 BodyIntent 各自映射到运动计划（预设动作库 / 实时规划 / 复合计划）：

## 6. 口型同步与表情

### 6.1 音频特征 → viseme 映射（接收 M4 AudioFeatureFrame）

M4 在 TTS 流式合成时，每帧（典型 30–50ms）提取音频特征推送给 M6：

```python
@dataclass
class AudioFeatureFrame:
    viseme_id: str      # 当前帧主导 viseme（如 "A" "O" "U" "M" "F" "rest"）
    volume: float       # 0..1

    timestamp_ms: int    # 音频时间戳（用于对齐）

```

**接收通道**：M4 → 共享环形缓冲（无锁单写多读）→ M6 每 tick 取最新帧。时延 < 30ms。

音素到 viseme 的映射参照经典 Preston Blair / Disney 12 原则，简化为 8 个 viseme：

| viseme_id | 音素示例 | mouth_open | mouth_width | lip_round |
|-----------|---------|-----------|-------------|-----------|
| A         | a/ai    | 0.8       | 0.6         | 0.0       |
| E         | e/ie    | 0.4       | 0.8         | 0.0       |
| I         | i       | 0.2       | 0.9         | 0.0       |
| O         | o/ou    | 0.5       | 0.2         | 0.7       |
| U         | u       | 0.3       | 0.1         | 0.9       |
| M         | m/b/p   | 0.0       | 0.3         | 0.0       |
| F         | f/v     | 0.1       | 0.5         | 0.0       |
| rest      | 静音    | 0.05      | 0.3         | 0.0       |

```python
VISEME_TABLE = {
    "A":   VisemeParam(mouth_open=0.8, mouth_width=0.6, lip_round=0.0),
    "E":   VisemeParam(mouth_open=0.4, mouth_width=0.8, lip_round=0.0),
    "I":   VisemeParam(mouth_open=0.2, mouth_width=0.9, lip_round=0.0),
    "O":   VisemeParam(mouth_open=0.5, mouth_width=0.2, lip_round=0.7),
    "U":   VisemeParam(mouth_open=0.3, mouth_width=0.1, lip_round=0.9),
    "M":   VisemeParam(mouth_open=0.0, mouth_width=0.3, lip_round=0.0),
    "F":   VisemeParam(mouth_open=0.1, mouth_width=0.5, lip_round=0.0),
    "rest":VisemeParam(mouth_open=0.05, mouth_width=0.3, lip_round=0.0),
}

def lip_sync_sample(audio_frame: AudioFeatureFrame) -> MouthParam:
    target = VISEME_TABLE.get(audio_frame.viseme_id, VISEME_TABLE["rest"])
    # 音量调制开口度（小声时嘴张小一点）
    vol_mod = 0.6 + 0.4 * audio_frame.volume
    # 平滑插值（避免嘴形跳变，30Hz 下时间常数 ~80ms）
    current = mouth_state.current
    alpha = min(1.0, CONTROL_DT / 0.08)
    new_open = lerp(current.open, target.mouth_open * vol_mod, alpha)
    new_width = lerp(current.width, target.mouth_width, alpha)
    new_round = lerp(current.round, target.lip_round, alpha)
    return MouthParam(open=new_open, width=new_width, round=new_round)
```

**为什么用 viseme 而非直接用音量驱动开口度**：纯音量驱动只能让嘴一开一合，看起来像咀嚼；viseme 让嘴形与音素对齐，看起来像在发音。

### 6.2 表情生成（情绪 / 姿态驱动面部 LED 或屏幕）

M2 不直接发情绪指令给 M6；情绪状态来自 M1 UserState（用户情绪）和 M2 自身姿态选择。M6 通过订阅 M2 的"姿态上下文"间接获得情绪标签。

```python
EMOTION_TO_FACE = {
    "neutral":     FaceFrame(eye_color=(180,180,180), brow=0.0,  mouth_curve=0.0),
    "happy":       FaceFrame(eye_color=(255,220,100), brow=0.2,  mouth_curve=0.5),
    "concerned":   FaceFrame(eye_color=(120,160,200), brow=-0.3, mouth_curve=-0.2),
    "thinking":    FaceFrame(eye_color=(150,150,255), brow=-0.1, mouth_curve=0.0),
    "apologetic":  FaceFrame(eye_color=(200,180,220), brow=-0.4, mouth_curve=-0.3),
}

def generate_face(emotion_tag: str, audio_frame: Optional[AudioFeatureFrame]) -> FaceFrame:
    base = EMOTION_TO_FACE.get(emotion_tag, EMOTION_TO_FACE["neutral"])
    if audio_frame is not None and audio_frame.is_speech:
        # 说话时把嘴形覆盖到面部
        mouth = lip_sync_sample(audio_frame)
        base = base.with_mouth(mouth)
    return base
```

**眨眼**：每 3–6 秒随机一次眨眼（200ms 闭眼），增加拟人感。眨眼期间嘴部不受影响。

**说话姿态与口型协同**：`SPEAKING_POSE` 是一个复合计划——基础说话姿态（头部随语调微动 + 偶发手势）+ 口型同步（音频驱动）。

```python
class SpeakingPlan(MotionPlan):
    def __init__(self, base_motion: PresetMotion, lip_sync_source):
        self.base = base_motion
        self.lip = lip_sync_source
        self.t_start = monotonic_now()

    def sample(self, t_now: float) -> JointTrajectoryPoint:
        t_rel = t_now - self.t_start
        # 基础姿态（头部随语调微动）
        base_pose = self.base.sample_loop(t_rel)
        # 头部偏航按基频微动（语调自然摆头）
        audio = self.lip.latest()
        if audio and audio.is_speech:
            head_yaw_mod = 0.05 * math.sin(2*math.pi * 0.5 * t_rel)
            base_pose["head_yaw"] += head_yaw_mod
        # 嘴形由 lip_sync 单独驱动（不进关节空间，进面部）
        return JointTrajectoryPoint(base_pose, face_extras={"audio": audio})
```

### 6.3 与 TTS 音频对齐（时间戳对齐 < 30ms）

**时间对齐**：M6 维护一个"音频播放时间戳"，与音频输出设备的实际播放时间同步。口型按播放时间而非接收时间采样，避免缓冲抖动导致口型领先/滞后于声音。

```python
# M6 侧：每个 tick 取最新音频帧并按播放时间采样
audio = audio_ring.latest()
if audio and (now - audio.recv_time) < 0.1:
    # 用音频时间戳对齐，而非 M6 接收时间
    playback_time = audio_output_device.current_playback_time()
    aligned_frame = audio_ring.sample_at(playback_time)
    mouth = lip_sync_sample(aligned_frame)
else:
    mouth = MouthParam.rest()  # 无音频或断流 → 闭嘴
```

**对齐误差预算**：< 30ms（主文档 §5.6 契约）。M4 → M6 共享内存通道时延 < 5ms，播放时间戳对齐误差 < 25ms，合计 < 30ms。

## 7. 安全机制

身体失控是物理安全问题，不是软件 bug。M6 安全机制是多层冗余设计。所有安全机制都在本地 RT 核完成，不依赖主脑 API、不依赖网络。

### 7.1 硬件急停按钮

**硬件急停**：本体上的物理按钮，直接切断执行器供电（继电器硬件回路，不经过软件）。这是最后一道闸门。

**软件急停**：
- M2 可发 `EStop` 命令（高优先级意图）
- M6 看门狗触发（100ms 无心跳）
- IMU 倾倒检测触发
- 任何 `SensorEvent(severity="critical")`

```python
def trigger_estop(reason: str):
    hal.emergency_stop()           # 切断执行器
    intent_queue.clear()            # 清空意图队列
    state.estop_active = True
    state.estop_reason = reason
    emit_sensor_event("estop", "critical", {"reason": reason})
    # 通知 M2
    m2_event_channel.send(SensorEvent("estop", "critical", {"reason": reason}))
```

**解除急停**：必须人工确认（物理按钮 + 软件命令双确认），M6 自身不能自动解除。

### 7.2 关节限位（软限位内缩 2° / 硬限位双保险）

三层限位：
1. **硬限位**：机械挡块（物理限制，不可超）
2. **软限位**：软件判断，比硬限位内缩 2°（见 §4.4）
3. **目标限幅**：规划阶段对每个目标做限幅（IK 求解后立即限幅）

软限位触发 → 该 tick 不写新目标，关节保持上一安全角度 → 上报 warning。

### 7.3 碰撞检测（自碰撞包围盒 / 外部碰撞触觉 + 距离）

- **自碰撞**：关节空间目标用球体/胶囊体包围盒做快速成对距离检查（< 0.3ms）。
- **外部碰撞**：触觉皮肤 + 距离传感器融合判定（见 §4.3 D 避障策略分层）。
- **碰撞响应**：碰撞发生 → 立即冻结相关关节 → 上报 → 等待 M2 决定重试或换姿态。

### 7.4 IMU 倾倒检测（35° 预警 / 60° 已倾倒冻结）

```python
def check_tilt(imu: IMUReading) -> Optional[SafetyResult]:
    # 重力向量与本体 z 轴的夹角
    g = np.array([imu.ax, imu.ay, imu.az])
    g_norm = g / np.linalg.norm(g)
    tilt = math.degrees(math.acos(g_norm[2]))  # 假设本体 z 轴垂直

    if tilt > 60:
        return SafetyResult.fail(f"FALL DETECTED: tilt={tilt}")
    if tilt > 35 and state.tilt_persistent_count > 5:  # 持续 > 50ms (5 tick @ 30Hz)
        return SafetyResult.fail(f"TILT WARNING: tilt={tilt}")
    state.tilt_persistent_count = state.tilt_persistent_count + 1 if tilt > 35 else 0
    return None
```

**倾倒响应**：冻结所有关节 + 底盘断电 + 上报 critical + 等待人工介入。

### 7.5 看门狗心跳（100ms 无心跳紧急冻结）

```
[M6 控制环] ──每 33ms──► [共享内存 heartbeat 计数器 + UDP 心跳包]
                                        │
                                        ▼
                        [独立看门狗进程/硬件] 每 33ms 检查一次
                                        │
                                100ms 内未更新？
                                        │ 是
                                        ▼
                                触发 hal.emergency_stop()
                                + 通知 M2
```

**看门狗独立性**：看门狗不与 M6 同进程，最好在独立硬件（如外置 MCU）或独立进程，避免 M6 进程崩溃时看门狗一起死。

**心跳内容**：

```python
class Heartbeat:

    tick_count: int        # 累计 tick 数

```

### 7.6 多层保护策略（任何不确定优先冻结）

安全机制的设计原则是**多层冗余 + 失败安全（fail-safe）**：

| 层 | 机制 | 触发 | 响应 |
|---|------|------|------|
| L0 | 硬件急停按钮 | 人工按下 | 物理切断执行器供电 |
| L1 | 软件急停 | M2 命令 / 看门狗 / 倾倒 / critical 事件 | hal.emergency_stop() |
| L2 | 关节软限位 | 目标角度超软限位 | 该 tick 不写新目标，保持上一安全角度 |
| L3 | 速度限制 | 角速度超 max_vel × 1.05 | 该 tick 不写新目标 |
| L4 | 自碰撞检测 | 包围盒相交 | 该 tick 不写新目标 |
| L5 | 外部碰撞检测 | 触觉触发 + 移动中 / 距离 < 0.15m | 立即停底盘 |
| L6 | IMU 倾倒 | 35° 预警 / 60° 已倾倒 | 冻结所有关节 + 底盘断电 |
| L7 | 看门狗 | 100ms 无心跳 | 独立硬件/进程触发紧急制动 |

**核心原则**：任何一层触发，优先冻结而非继续运动。"不确定优先冻结"是 M6 的安全底线——宁可身体僵住让用户重启，也不能让身体失控伤人。

## 8. 降级与容错

按失效模式分级降级，保证"不失控"是底线。降级后**绝不自动恢复**到全功能，必须显式收到"恢复"指令（来自 M2 或人工）。

### 8.1 单关节失效（被动模式保持当前角度）

| 失效模式 | 检测 | 降级行为 | 上报 |
|---------|------|---------|------|
| 单关节编码器失效 | 编码器读数与 IMU 估计差异 > 5° 持续 100ms | 该关节进入被动模式（保持当前角，不接收指令） | warning + BodyAck aborted |
| 单关节舵机过热 | 温度 > 70°C | 该关节降速到 30% | warning |
| 单关节完全卡死 | 力矩超阈值但位置不动 | 该关节冻结，其余关节继续 | warning + BodyAck aborted |

**被动模式**：失效关节保持当前角度（舵机抱闸），不再接收新指令。其余关节正常运动，规划时把失效关节当作"固定参数"处理。这样局部失效不会让整个身体瘫痪。

### 8.2 传感器失效（编码器与 IMU 差异超阈值进入降级）

| 失效模式 | 检测 | 降级行为 | 上报 |
|---------|------|---------|------|
| IMU 失效 | IMU 数据冻结或 NaN | 倾倒检测不可用 → 禁止移动（底盘 v=0），上身动作可继续 | warning |
| 触觉失效 | 触觉数据全 0 持续 5s | 碰撞检测降级为仅距离传感器，移动速度上限降到 50% | warning |
| 距离传感器失效 | 数据冻结或 NaN | 禁止 APPROACH_USER，已移动的慢慢减速到 0 | warning |

**IMU 失效的特别处理**：IMU 是倾倒检测的唯一来源，IMU 失效时倾倒检测不可用——这是高风险状态。M6 立即禁止底盘移动（避免移动中倾倒无法检测），上身动作可继续（上身动作倾倒风险低）。上报 warning 等待 M2 决定是否进入 L5 降级（身体冻结对话继续）。

### 8.3 通讯断（M6 自主维持基本姿态与安全，L5 身体冻结对话继续）

| 失效模式 | 检测 | 降级行为 | 上报 |
|---------|------|---------|------|
| M2 通讯断 | 2s 无新 BodyIntent | 保持当前姿态，进入 IDLE_BREATH 待机 | critical to M2（恢复后） |
| M4 音频断 | 1s 无 AudioFeatureFrame | 口型归零（闭嘴），表情保持 | info |
| 控制环超时 | 单 tick > 33ms | 降低运动速度上限到 50%，连续 5 tick 超时 → 冻结 | warning |
| 主进程崩溃 | 看门狗 100ms 无心跳 | 硬件急停 + 通知 M2 | critical |
| 完全断电 | — | 硬件回路保持舵机抱闸（机械制动） | — |

**M2 通讯断的关键设计**：M6 检测到 2s 无新 BodyIntent 时，**不冻结**，而是进入 IDLE_BREATH 待机姿态——保持基本姿态与安全，等待 M2 恢复。这与主文档 §8.1 L5 降级（身体失效冻结对话继续）相反方向：L5 是 M6 挂了对话继续，这里是 M2 挂了身体继续维持。两者都是"局部失效不导致全局瘫痪"原则的体现。

**M2 通讯断时的规则兜底**：M6 用本地规则维持基本行为：
- 若当前在执行 APPROACH_USER，继续走到目标点后停下（不中途停在危险位置）
- 若当前在执行 SPEAKING_POSE，1s 无音频后转为 IDLE
- 任何安全事件（倾倒/碰撞/急停）照常处理，不依赖 M2

### 8.4 主脑 API 不可用（M6 不依赖主脑 API，身体仍正常运动）

**这是 M6 与主脑 API 彻底解耦的核心体现**。主脑 API（DeepSeek/OpenAI）故障场景包括：401/403 鉴权失败、超时、网络断、服务端 5xx。

**M6 的响应**：**完全不响应**——M6 既不调用主脑 API，也不感知其状态。主脑 API 不可用时：

| 场景 | α/β 路径行为 | M6（γ 路径）行为 |
|------|-------------|----------------|
| 主脑 API 超时 | L3 降级：M2 用规则兜底占位"让我想想..." | 不受影响，继续执行已下发的 BodyIntent |
| 主脑 API 401/403 | L7 降级：M3 切备用 API（OpenAI↔DeepSeek 互备） | 不受影响 |
| 主脑 API 全断 | L7 极端：副脑本地 Qwen2.5-3B 应急生成（降级质量） | 不受影响 |
| 网络断 | ASR/TTS 也受影响，可能转纯文本 | 不受影响，身体照常运动 |

**唯一例外——SPEAKING_POSE 口型同步**：SPEAKING_POSE 依赖 M4 音频特征做口型同步。主脑 API 不可用时，M4 没有 TTS 音频产出 → M6 收不到 AudioFeatureFrame → 口型归零（闭嘴），表情保持待机状态。但身体姿态控制（头部微动、手势等）仍正常执行。

```python
# SPEAKING_POSE 在无音频时的退化
class SpeakingPlan(MotionPlan):
    def sample(self, t_now: float) -> JointTrajectoryPoint:
        t_rel = t_now - self.t_start
        base_pose = self.base.sample_loop(t_rel)  # 基础说话姿态仍执行
        audio = self.lip.latest()
        if audio and audio.is_speech:
            # 有音频：正常口型同步
            head_yaw_mod = 0.05 * math.sin(2*math.pi * 0.5 * t_rel)
            base_pose["head_yaw"] += head_yaw_mod
        else:
            # 无音频（主脑 API 挂 / TTS 断 / 静音段）：闭嘴 + 待机表情
            # 但基础说话姿态保持，不冻结
            pass
        return JointTrajectoryPoint(base_pose, face_extras={"audio": audio})
```

**M2 侧的编排调整**：主脑 API 不可用时，M2 会感知到（M3 上报 API 故障），M2 应避免下发 SPEAKING_POSE（因为没有音频可同步），改为下发 THINKING_POSE（思考姿态，不依赖音频）或 IDLE。这由 M2 决策，M6 不主动感知主脑 API 状态。

**结论**：主脑 API 故障是 α/β 路径的问题，不是 γ 路径的问题。M6 的身体控制环完全自包含，主脑 API 挂掉时 Lucy 的身体仍能维持姿态、执行动作、保证安全——只是没有"说话"这件事的口型同步。这是新架构（主脑 API 化）相对旧架构（主脑本地 GPU）在身体侧的韧性优势：旧架构 GPU 故障时主脑全瘫，可能影响 M2 决策导致身体也无指令；新架构主脑 API 故障时副脑仍能维持身份守卫与决策，身体侧完全不受影响。

## 9. 与 M2/M4 的耦合

M6 的跨模块耦合仅与 M2（意图下发）和 M4（音频特征）发生，与主脑 API、M3、M1、M5 无直接数据流耦合。

### 9.1 接收 M2 BodyIntent（异步 / 回执 < 50ms）

- **通道**：本地 socket 或共享内存 + 无锁队列
- **协议**：异步、非阻塞、覆盖式语义
- **M2 不阻塞**：M2 push 后立即返回，不等 M6 执行完
- **M6 不回压**：意图队列满则丢弃最旧，不向 M2 反压
- **回执**：M6 在 BodyIntent 生命周期内多次回执（accepted → executing → done/aborted），延迟 < 50ms
- **不依赖主脑 API**：M2 下发 BodyIntent 是副脑决策的结果，副脑决策可能调主脑 API（β 路径思考模式），但 M6 只接收最终的 BodyIntent，不感知其决策过程是否涉及主脑 API

```python
# M2 侧
m2.send_to_m6(IntentEnvelope(intent=BodyIntent.WAVE, intent_id=uuid(), priority=1, params={}))
# 立即返回，不等 M6

# M6 侧
env = intent_queue.latest()
if env is not None and env.intent_id != state.current_intent_id:
    state.set_new_intent(env)
    emit_ack(env.intent_id, "accepted", 0.0)
```

### 9.2 接收 M4 音频特征（流式 / < 30ms）

- **通道**：共享内存环形缓冲（无锁单写多读）
- **协议**：流式、最新值优先（M6 不消费历史帧）
- **时间对齐**：M6 按音频播放时间戳采样口型，对齐误差 < 30ms
- **断流处理**：1s 无音频帧 → 闭嘴 + 表情保持（不影响身体姿态控制）
- **不依赖主脑 API**：M4 的 TTS 音频来自主脑 API 生成的 token（α/β 路径），主脑 API 挂时 M4 无音频产出，M6 口型归零但身体控制照常

```python
# M4 侧：每个 TTS 帧 push 到共享缓冲
audio_ring.push(AudioFeatureFrame(viseme_id="A", volume=0.6, f0=180, timestamp_ms=..., is_speech=True))

# M6 侧：每个 tick 取最新
audio = audio_ring.latest()
if audio and (now - audio.recv_time) < 0.1:
    mouth = lip_sync_sample(audio)
else:
    mouth = MouthParam.rest()
```

### 9.3 推送传感器事件到 M2

M6 不主动向 M2 推送高频遥测（避免反向耦合），只在事件发生时推送 SensorEvent（touch/tilt_warning/obstacle/estop/joint_fault）。M2 收到事件后决定是否调整后续 BodyIntent 下发策略。

**关键**：M6 → M2 的事件推送是单向的，M2 不向 M6 反压。即使 M2 卡顿不处理事件，M6 的安全机制照常工作（安全检查在本地完成，不依赖 M2 响应）。

## 10. 时延管理与三路径分离

### 10.1 γ 路径独立 RT 核最高优先级

主文档 §4.2 三路径分离原则要求 γ 路径"独立 RT 核，禁迁移，最高优先级"。M6 的实现：

| 维度 | 实现 | 与主文档对齐 |
|------|------|-------------|
| 线程模型 | 独立 RT 线程（SCHED_FIFO，优先级 80） | 主文档 §4.2 |
| CPU 亲和性 | 绑定独立 RT 核（RT_CORE_ID），禁迁移 | 主文档 §4.2 + §9 部署拓扑 |
| 内存 | mlockall 锁定，预分配缓冲，运行时不 new | 主文档 §4.2 资源隔离 |
| 网络 | 控制环内零网络调用（不调主脑 API、不调 M5、不查云端） | M6 特有约束 |
| 看门狗 | 独立进程/硬件，100ms 无心跳触发紧急制动 | 主文档 §8.2 |

### 10.2 绝不阻塞 α/β

γ 路径与 α/β 路径的资源隔离：

| 资源 | α 路径 | β 路径 | γ 路径（M6） |
|------|--------|--------|-------------|
| CPU | 对话核（2核） | 后台核（1核） | RT 核（1核，隔离） |
| GPU | 副脑本地 forward（优先） | 空闲时用 | **不用** |
| 内存 | 副脑 KV Cache + identity_cache | 预计算缓存（2GB） | 控制器状态（小，预分配） |
| 网络 | 主脑 API + TTS/ASR | 主脑 API 思考模式 | **不用**（零网络调用） |

**冲突仲裁**（主文档 §4.2）：
- α/β 与 γ 抢 CPU：γ 绝对优先。身体失控会摔倒，是安全问题。
- γ 不抢 GPU、不抢网络——M6 的控制环纯 CPU + 本地总线，与 α/β 的资源几乎没有交集。

**关键约束**：γ 路径的控制环内**绝不调用**任何可能阻塞的外部服务：
- 不调主脑 API（网络 IO，可能超时）
- 不调 M5 工具（可能阻塞）
- 不读 M1 UserState（改为 M2 转译为 BodyIntent 下发）
- 不查云端地图（导航用本地传感器反应式避障）

这保证了 γ 路径的时序确定性——控制环周期只受本地 CPU 与总线影响，不受网络抖动影响。

## 11. 结语

M6 是 Lucy"有身体"的工程落地。它把 M2 副脑的高级意图翻译成关节空间的毫秒级动作，把 M4 的音频特征翻译成嘴形与表情，同时通过多层安全机制保证任何失效都不会让身体失控。

M6 的设计核心是**"意图级接口 + 本地自主 + 安全优先 + 与主脑 API 彻底解耦"**：
- 意图级接口让 M2 不被低层细节拖慢；
- 本地自主让 M6 不被网络或 M2 节奏牵制；
- 安全优先让"具身"这件事不会变成"危险"；
- 与主脑 API 彻底解耦让主脑 API 故障（云端 LLM 不可用/网络断）时身体仍正常运动——这是新架构（主脑 API 化）在身体侧的韧性优势。

在三路径架构中，γ 路径虽然不直接产生对话内容，但它给 Lucy 提供了**"活着"的物理证据**——点头、注视、挥手、走向用户、托腮思考——这些动作让 Lucy 不再只是一个聊天框，而是一个有身体的对话伙伴。更关键的是，当主脑 API 故障、α/β 路径降级为纯文本或应急生成时，γ 路径的身体仍能维持姿态与安全——Lucy 的"身体活着"不依赖"主脑活着"，这与系统整体命题"具身的、全模态的、主动的对话机器人"在物理层面对齐。
