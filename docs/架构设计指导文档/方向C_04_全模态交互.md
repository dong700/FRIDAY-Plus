## 1. 摘要

Lucy 的主脑是外部 LLM API（DeepSeek/OpenAI 兼容，权重只读、被调用才说话），副脑（M2，Qwen2.5-3B + V30）只输出结构化 `DialogueIntent` 并经 M3 把意图序列化为 API 请求、流式接收、W_probe 异己过滤后回送干净 token 流。真正把这些抽象产物变成"用户听得见、看得见、能感知"的对话体验的，是模块4（M4）。M4 同时承担两个方向的工作：

- **输入侧（不变）**：采集麦克风/摄像头/键盘三路原始流，做流式 ASR（火山引擎端到端）、视觉感知（人脸/情绪/presence/注意力 4 任务并行）、文本归一，并把这些低层信号融合成结构化事件推送给 M1（更新 UserState）和 M2（触发 α 路径）。
- **输出侧（大改）**：从 M3 接收**已过滤异己的干净 token 流**（M4 不做异己检测），做**分句 → TTS 流式合成 → 音频流**，同时把 token 流并行分发到字幕显示与 M6 口型同步驱动。

M4 的核心难点不是单点能力，而是**流式管线的零等待编排**：主脑 API token 流不能等整段生成完再 TTS（API 首 token 500–2000ms、方差大），TTS 不能等整句再合成，字幕不能等音频播完再显示。三者必须以"句子边界 + 音频特征"为同步锚点并行推进，并在用户偏好（TTS 播完后字幕右移、字幕置于 canvas 外避免遮挡 avatar、avatar 居中不被截断）与时延预算（首 token 端到端 < 2.0s、首音频端到端 < 2.5s）之间取得平衡。

### 核心数据契约

```python
# M4 输入侧 → M2（α 路径启动）
@dataclass
class SpeechStartEvent:
    timestamp: float          # 单调时钟
    partial_text: str = ""    # ASR 首 chunk 部分文本
    confidence: float = 0.0

# M4 输入侧 → M1（更新 UserState）
@dataclass
class PresenceEvent:
    timestamp: float
    present: bool             # 是否在场
    bbox: Optional[Tuple[int,int,int,int]] = None  # 人脸框
    num_faces: int = 0

@dataclass
class VisualState:
    presence: bool
    attention: float          # 0..1，看向 Lucy 的程度
    emotion: str              # happy/sad/neutral/angry/surprise
    emotion_confidence: float
    face_bbox: Optional[Tuple[int,int,int,int]]

# M3 → M4 输出侧（已过滤异己的干净 token 流）
@dataclass
class TokenChunk:
    text: str
    is_final: bool = False    # 是否为流式 token（非终结）
    finish_reason: Optional[str] = None   # "stop" / "length" / "filtered"
    sentence_id_hint: Optional[int] = None  # M3 可选给出当前所属句子序号

# M4 输出侧 → 前端/M6
@dataclass
class TTSAudioChunk:
    audio_bytes: bytes        # PCM/MP3 分片
    sample_rate: int
    viseme: Optional[str] = None  # 当前音素→口型（给 M6）
    sentence_id: int = 0      # 句子序号，用于字幕同步
    is_last_in_sentence: bool = False

@dataclass
class SubtitleSegment:
    text: str
    sentence_id: int
    tokens: List[str]         # 逐 token 时间戳
    played: bool = False      # TTS 是否已播完
```

### 时延契约（对齐主文档 §4.1）

| 项 | 预算 | 目标 | 阻塞 α? |
|---|---|---|---|
| ASR 首 chunk | 500ms | 300ms | 是 |
| 视觉检测延迟 | 100ms | 50ms | 否（旁路） |
| 主脑 API 首 token（网络+推理） | 1500ms（500–2000ms 方差大） | 1000ms | 是（M3 负责） |
| TTS 首音频 | 400ms | 300ms | 是 |
| **首 token 端到端** | **2.0s** | **1.5s** | 是（含 API 网络） |
| **首音频端到端** | **2.5s** | **2.0s** | 是（含 API + TTS） |
| 字幕同步偏移 | ±150ms | ±80ms | 否（用户体验） |
| 口型同步偏移 | <50ms | <30ms | 否（γ 路径插值兜底） |

**关键变化**（vs 旧架构）：
- 旧：主脑本地 GPU 首 token 800–1500ms，M4 直连主脑拿 token
- 新：主脑 API 首 token 500–2000ms（均值相当、方差更大），M4 从 M3 接收**已过滤异己**的 token 流（M3 在副脑本地 GPU 上跑 W_probe batch 检测，与 API 流式接收并行，不显著阻塞）
- M4 的时延杠杆 unchanged：VAD 即推 SpeechStartEvent（让 M2/M3 提前开始）+ 流式分句 + TTS 重叠合成

### 2.2 边界与不做的事

| M4 做 | M4 不做 |
|---|---|
| 三路原始流采集与预处理 | 不做用户建模（M1 职责） |
| 流式 ASR / TTS 调度 | 不做对话决策（M2 职责） |
| 视觉感知 4 任务（人脸/情绪/presence/注意力） | 不做语言生成（主脑 API 职责） |
| 事件推送（SpeechStart/Presence） | **不做异己检测**（M3 在副脑本地 GPU 上跑 W_probe，M4 只接收已过滤的干净 token 流） |
| token 流分句 + 三路并行分发 | 不做主脑 API 客户端管理（M3 职责） |
| 字幕显示规则（右移动画、canvas 外布局） | 不做身体运动控制（M6 职责） |
| 口型/音频特征信号输出 | 不持久化对话历史 |

**架构反转带来的边界变化**：旧 M4 直连主脑本地 GPU 拿 token；新 M4 不再直连主脑，而是从 M3 拿干净 token 流。这一变化让 M4 的输出侧管线职责更纯粹——"只管把 token 流变成可听可见的对话体验，不管 token 是不是 Lucy 风格"。异己过滤、重生成、API 客户端管理全部归 M3。

### 2.3 与三路径的关系

M4 同时参与 α 与 β 两条路径，不进入 γ 路径（身体控制环）：

- **α 路径（主战场）**：用户开口 → ASR 首 chunk → 推 SpeechStartEvent → M2 快速判定 → M3 调主脑 API 流式生成 + W_probe 过滤 → M4 接收干净 token 流 → 流式 TTS + 字幕 + 口型。**这是 M4 的主战场，时延预算最硬。**
- **β 路径（预计算受益方）**：M2 主动发起 → M3 调主脑 API 预生成（带 W_probe 过滤）→ M4 预合成 TTS 音频缓存 → 时机到直接播放。M4 在 β 路径中是"预计算受益方"，可提前合成、近 0 延迟播放。
- **γ 路径（仅单向信号输出）**：M4 只通过"音频特征 → M6 viseme"做单向信号输出，不参与控制环。

## 3. 输入 Pipeline

输入侧在架构反转后**完全不变**——三路原始流采集、流式 ASR、视觉感知 4 任务、文本归一、事件推送全部复用旧实现。理由：架构反转改的是"主脑从哪来"，输入侧只关心"用户的感官信号怎么变成事件推给 M1/M2"，与主脑位置无关。

### 3.1 语音输入（ASR 流式，火山引擎端到端）

#### 3.1.1 选型与理由

采用**火山引擎端到端语音对话**提供的流式 ASR，而非本地 Whisper/Paraformer。理由：

| 维度 | 火山引擎端到端 | 本地 Whisper-large | 本地 Paraformer |
|---|---|---|---|
| 首 chunk 延迟 | 200–400ms | 800ms+（整句） | 300–500ms |
| 流式能力 | 原生流式 | 仅 VAD 切分后整句 | 流式 |
| 中文识别准确率 | 高（专为中文优化） | 中 | 高 |
| 资源占用 | 云端，不占本地 GPU | 占满本地 GPU | 占本地 GPU |
| 端到端集成 | ASR+TTS 一体化 | 仅 ASR | 仅 ASR |

副脑 Qwen2.5-3B + V30 已占用边缘 GPU 跑轻量 forward（状态感知/异己检测/身份维持），ASR 不能再抢本地 GPU 资源。火山引擎云端流式 ASR 满足 500ms 首 chunk 预算，且与 TTS 同源，便于音色一致性。

#### 3.1.2 流式采集架构

```python
# 伪代码：ASR 流式采集与事件推送
import asyncio
from collections import deque

class ASRStreamPipeline:
    def __init__(self, volc_app_id, volc_token):
        self.client = VolcanoASRClient(app_id=volc_app_id, token=volc_token)
        self.audio_buf = deque()           # 麦克风环形缓冲
        self.chunk_size = 320              # 20ms @ 16kHz, 16bit
        self.vad = VAD(min_speech=300, max_silence=800)
        self._speech_started = False

    async def run(self, mic_stream: AsyncIterator[bytes]):
        async for chunk in mic_stream:
            self.audio_buf.append(chunk)
            # 推送音频到火山引擎流式 ASR
            partial = await self.client.feed(chunk)
            # VAD 检测用户开口
            if self.vad.is_speech_start(chunk) and not self._speech_started:
                self._speech_started = True
                await self._emit_speech_start(partial)
            # partial 文本累积，最终 final 时推送完整文本给 M2
            if partial.is_final:
                await self._emit_final_text(partial.text)
                self._speech_started = False

    async def _emit_speech_start(self, partial):
        """α 路径启动信号——不等 ASR 完成，立即推 M2"""
        event = SpeechStartEvent(
            timestamp=time.monotonic(),
            partial_text=partial.text,
            confidence=partial.confidence,
        )
        await self.event_bus.publish("m2.speech_start", event)
```

#### 3.1.3 首 chunk 优化要点

- **VAD 触发即推**：不等 ASR 返回文本，VAD 检测到语音起始（300ms）就推 `SpeechStartEvent` 给 M2，让 M2 提前开始读 UserState + 记忆检索、M3 提前组装身份 prompt。这是 α 路径时延最大杠杆之一——把"串行等 ASR 完整文本再启动主脑"改为"VAD 一响就并行启动"。
- **音频分片大小**：20ms（320 samples @ 16kHz）一块，平衡网络开销与首 chunk 延迟。
- **连接预热**：M4 启动时即与火山引擎建立 WebSocket 长连接，避免每次说话都握手（省 ~80ms）。

### 3.2 视觉输入（人脸检测/情绪识别/presence/注意力）

视觉感知是 4 个并行子任务，全部在本地 CPU 上运行（**不抢副脑 GPU**——副脑 GPU 跑 Qwen2.5-3B + V30 的状态感知/异己检测 forward），总延迟 < 100ms，且**绝不阻塞 α 路径**——视觉结果是"旁路信号"，慢一点只影响 UserState 更新精度，不影响首音频延迟。

子任务详见 §6，本节给出输入侧的采集与分发流程：

```python
class VisionPipeline:
    def __init__(self):
        self.face_det = MediaPipeFaceDetector()      # §6.1
        self.emo_rec = FERPlusEmotionClassifier()    # §6.2
        self.presence = PresenceChecker()            # §6.3
        self.gaze = GazeAttentionEstimator()         # §6.4

    async def run(self, camera_stream: AsyncIterator[Frame]):
        async for frame in camera_stream:  # 30 FPS
            t0 = time.monotonic()
            # 4 任务并行（CPU 多线程）
            faces = await self.face_det.detect(frame)
            emo = await self.emo_rec.classify(frame, faces) if faces else None
            pres = self.presence.check(faces)
            att = self.gaze.estimate(frame, faces) if faces else 0.0
            # 打包 VisualState 推 M1
            vs = VisualState(presence=pres, attention=att,
                             emotion=emo.label if emo else "neutral",
                             emotion_confidence=emo.conf if emo else 0.0,
                             face_bbox=faces[0].bbox if faces else None)
            await self.event_bus.publish("m1.visual_state", vs)
            # presence 状态变化时推 PresenceEvent
            if self._presence_changed(vs.presence):
                await self.event_bus.publish("m1.presence",
                    PresenceEvent(timestamp=time.monotonic(),
                                  present=vs.presence,
                                  bbox=vs.face_bbox, num_faces=len(faces)))
            assert (time.monotonic() - t0) < 0.1  # < 100ms 硬约束
```

### 3.3 文本输入（键盘/触摸屏）

文本输入走前端 WebSocket，是 α 路径的"轻量入口"——无 ASR 延迟，直接进 M2：

```python
# 后端 FastAPI WebSocket 处理文本输入
@app.websocket("/ws/text")
async def text_input(ws: WebSocket):
    await ws.accept()
    while True:
        msg = await ws.receive_json()
        if msg["type"] == "text_submit":
            # 文本输入立即触发 SpeechStartEvent（等价语义）
            await event_bus.publish("m2.speech_start",
                SpeechStartEvent(timestamp=time.monotonic(),
                                 partial_text=msg["text"], confidence=1.0))
            await event_bus.publish("m2.final_text", msg["text"])
```

文本输入的延迟模型：网络 RTT（~20ms 局域网）+ 事件总线（~5ms）≈ 25ms，远优于语音路径。

### 3.4 多模态融合（语音 + 视觉 + 文本 → 事件）

M4 的融合策略是**"事件级融合"而非"特征级融合"**——不做端到端多模态编码（成本高、且主脑是纯文本 API），而是把各路信号降维成结构化事件，由 M1/M2 决定如何用。

| 融合场景 | 输入信号 | 输出事件 | 消费方 |
|---|---|---|---|
| 用户开口 | ASR VAD + 视觉 presence | SpeechStartEvent（带 face_bbox） | M2 |
| 用户离开 | 视觉 presence=False 持续 2s | PresenceEvent(present=False) | M1 |
| 用户看向 Lucy | 视觉 attention > 0.7 | AttentionEvent | M1 |
| 用户情绪突变 | 情绪从 neutral→sad | EmotionShiftEvent | M1 + M2 |
| 用户说话+看屏 | ASR 在说 + attention<0.3 | DistractedEvent | M2（影响回复策略） |

融合规则采用"时间窗对齐"：100ms 窗口内多路信号合并为同一事件包，避免事件风暴。

### 3.5 事件推送协议（SpeechStartEvent / PresenceEvent）

事件总线采用**单写多读 + 主题订阅**模型，所有跨模块事件经统一总线分发，避免点对点耦合：

```python
# 事件总线接口（伪代码）
class EventBus:
    async def publish(self, topic: str, payload: Any) -> None: ...
    def subscribe(self, topic: str, handler: Callable) -> None: ...

# 主题命名约定
TOPICS = {
    "m2.speech_start":   "M4 → M2：用户开口，启动 α 路径",
    "m2.final_text":     "M4 → M2：ASR 完整文本",
    "m1.presence":       "M4 → M1：用户在场状态变化",
    "m1.visual_state":   "M4 → M1：视觉态实时更新（10Hz）",
    "m1.attention":      "M4 → M1：注意力变化",
    "m1.emotion_shift":  "M4 → M1：情绪突变",
    "frontend.subtitle": "M4 → 前端：字幕段",
    "frontend.tts_audio":"M4 → 前端：TTS 音频流",
    "m6.viseme":         "M4 → M6：口型/音素信号",
}
```

**事件可靠性**：所有 `m2.*` 主题走可靠队列（持久化 + ACK），其余走最佳努力（丢一帧视觉态不影响功能）。`SpeechStartEvent` 丢失会导致 α 路径不启动——必须保证投递。

## 4. 输出 Pipeline（大改：主脑 token 流来源从本地 GPU 改 M3 API 流式接收）

输出侧是架构反转的**主要改动区**。旧 M4 直连本地 Qwen2.5-3B 主脑拿 token；新 M4 从 M3 接收**已过滤异己的干净 token 流**，主脑 API 调用、身份 prompt 注入、W_probe 生成后异己检测、重生成降级全部归 M3。

### 4.1 token 流接收（从 M3 接收已过滤异己的干净 token 流）

#### 4.1.1 数据契约

M3 通过 `GenerationStream` 接口向 M4 暴露已过滤异己的 token 流（详见主文档 §5.3 / M3 文档）：

```python
# M3 → M4 接口（M4 只读，不写）
class GenerationStream:
    def tokens(self) -> Iterator[str]: ...           # 已过滤异己的 token
    def alien_report(self) -> Optional[AlienReport]: ...  # 异己检测汇总（M4 仅记录，不处理）
    def finish_reason(self) -> str: ...
```

M4 的输出侧管线订阅 `m3.token_stream` 主题，逐 token 消费。M4 **不做**任何异己检测——异己过滤、缓冲、重生成全部在 M3 完成（M3 在副脑本地 GPU 上跑 W_probe batch forward，与主脑 API 流式接收并行，不显著阻塞）。

#### 4.1.2 接收实现

```python
# m4/output_pipeline.py（接收侧）
class TokenStreamReceiver:
    """从 M3 接收已过滤异己的干净 token 流"""
    def __init__(self, event_bus):
        self.bus = event_bus
        self._queue: asyncio.Queue[TokenChunk] = asyncio.Queue()
        self._alien_log: list = []  # 仅记录，不处理

    async def on_token(self, chunk: TokenChunk):
        """M3 通过事件总线推 token，M4 入队"""
        await self._queue.put(chunk)

    async def on_alien_report(self, report: AlienReport):
        """M3 在流结束时推异己汇总报告，M4 仅记录用于评估"""
        self._alien_log.append(report)

    async def stream(self) -> AsyncIterator[str]:
        """M4 输出管线消费 token 流"""
        while True:
            chunk = await self._queue.get()
            if chunk.is_final:
                break
            yield chunk.text
```

#### 4.1.3 为什么 M4 不做异己检测

| 维度 | 旧架构（M4 直连主脑） | 新架构（M4 接 M3） |
|---|---|---|
| 异己检测执行位置 | 旧 M3 在副脑本地 GPU | M3 在副脑本地 GPU（同位置，职责重新划分） |
| M4 是否参与 | 否 | 否（unchanged） |
| M4 接收的 token | 本地主脑原始 token | M3 过滤后的干净 token |
| 时延影响 | 异己 batch ~10ms 与本地生成并行 | 异己 batch ~10ms 与 API 接收并行，不显著阻塞 |

**设计要点**：M3 的 W_probe 异己检测按 token batch（每 16 token 一次本地 forward）与 API 流式接收**并行**进行，异己分数超阈值的句子被缓冲在 M3 不送 M4，触发 M3 重生成或降级。M4 看到的是"已通过的干净流"，时延上仅增加 ~10ms/batch 的副脑 forward（与 API 网络往返重叠），不显著阻塞。

### 4.2 分句器（标点。！？，或 20 字阈值触发 TTS）

主脑 API 以 token 流形式产出（首 token 500–2000ms，后续 token ~30–80ms/个，方差大于本地 GPU）。M4 的"分句器"持续累积 token，达到**句子边界**时切出一句送 TTS。

#### 4.2.1 边界判定规则

```python
SENTENCE_END_PUNCT = {"。", "！", "？", "!", "?", "…"}
CLAUSE_PUNCT = {"，", ",", "；", ";"}
MAX_LEN_THRESHOLD = 20   # 字符数阈值

class SentenceSegmenter:
    def __init__(self):
        self.buf = ""
        self.sentence_id = 0

    def feed(self, token: str) -> Optional[SubSent]:
        """返回 None 表示仍在累积；返回 SubSent 表示一句切出"""
        self.buf += token
        # 规则1：句末标点 → 立即切
        if any(p in token for p in SENTENCE_END_PUNCT):
            return self._cut()
        # 规则2：子句标点 + 已累积 ≥ 8 字 → 切（避免碎句）
        if any(p in token for p in CLAUSE_PUNCT) and len(self.buf) >= 8:
            return self._cut()
        # 规则3：长度阈值（无标点长句）→ 切
        if len(self.buf) >= MAX_LEN_THRESHOLD:
            return self._cut()
        return None

    def _cut(self) -> SubSent:
        s = SubSent(text=self.buf, id=self.sentence_id)
        self.sentence_id += 1
        self.buf = ""
        return s
```

#### 4.2.2 分句参数权衡

| 参数 | 值 | 过小 | 过大 |
|---|---|---|---|
| 句末标点 | 立即切 | — | — |
| 子句标点切长度 | 8 字 | 碎句，TTS 频繁起音不自然 | 长句合成延迟大 |
| 无标点长度阈值 | 20 字 | 同上 | 首 audio 等太久 |

实测建议：火山引擎 TTS 单句合成首音频 ~300–400ms，单句越长首音频越晚。**首句建议 ≤15 字**以保证首音频预算，后续句可放宽到 20–30 字。

### 4.5 M6 口型同步（音频特征 → viseme 序列 → M6）

M4 不直接驱动舵机（那是 M6 职责），但 M6 的口型同步需要"当前该张多大嘴、什么口型"的实时信号。M4 从 TTS 音频流中提取特征推送给 M6：

| 信号 | 提取方式 | 推送频率 | M6 用途 |
|---|---|---|---|
| viseme（音素→口型类） | 火山引擎 TTS 可返回音素时间戳 | 每 50ms | 选择预设口型帧 |
| 音量包络 | RMS 计算 | 每 20ms | 张嘴幅度（0–1） |
| 基频 F0 | YIN 算法 | 每 30ms | 语调→表情微调 |

```python
async def audio_to_viseme_stream(audio_iter: AsyncIterator[TTSAudioChunk]):
    async for chunk in audio_iter:
        rms = compute_rms(chunk.audio_bytes)
        f0 = estimate_f0(chunk.audio_bytes, chunk.sample_rate)
        viseme = chunk.viseme or "silence"
        await event_bus.publish("m6.viseme", {
            "viseme": viseme, "amplitude": rms, "f0": f0,
            "timestamp": time.monotonic(),
        })
```

M6 收到后做 30–60Hz 的插值驱动（γ 路径），保证口型与音频严格同步（偏移 < 50ms）。

## 5. 流式管线编排（核心）

本节是 M4 的**设计重心**。主脑 API token 流不能等生成完再 TTS——这是 α 路径首音频延迟的最大杠杆。架构反转后这一杠杆**更加关键**：主脑 API 首 token 500–2000ms 且方差更大，唯有流式分句+TTS 重叠能把它压在 2.5s 预算内。

### 5.1 token 流分句策略

M3 把干净 token 流推到 `m3.token_stream` 主题，M4 的分句器持续累积 token，达到句子边界时切出一句送 TTS。

#### 5.1.1 分句器实现

见 §4.2.1 的 `SentenceSegmenter`。

#### 5.1.2 分句参数权衡

见 §4.2.2。首句建议 ≤15 字以保证首音频预算。

### 5.2 TTS 流式合成

分句器输出的句子立即进 TTS 队列，TTS 边收句子边出音频：

```python
async def streaming_output_pipeline(token_iter: AsyncIterator[str]):
    segmenter = SentenceSegmenter()
    tts = TTSStreamPipeline(...)

    # 1. token → 分句器 → 句子流
    async def sentence_stream():
        async for token in token_iter:
            sub = segmenter.feed(token)
            if sub:
                yield sub
        # flush 残留
        if segmenter.buf:
            yield SubSent(text=segmenter.buf, id=segmenter.sentence_id)

    # 2. 句子流 → TTS → 音频流
    audio_iter = tts.stream(sentence_stream())

    # 3. 三路并行分发
    await asyncio.gather(
        _route_audio_to_speaker(audio_iter),    # 扬声器
        _route_tokens_to_subtitle(token_iter),  # 字幕
        _route_audio_to_viseme(audio_iter),     # M6 口型
    )
```

**关键**：`asyncio.gather` 让三路并行，不互相阻塞。字幕跟随 token 流（最快），音频跟随分句+TTS（稍慢），口型跟随音频（最慢但严格同步）。

### 5.3 字幕/token/口型三路并行输出

三路的同步关系是流式管线的精髓：

```
时间轴 ──────────────────────────────────────────▶

token流:  [抱歉][听到][这个][消息][，][我][也][很][难过][。]
            │     │     │     │    │   │   │    │    │
字幕:     抱歉听到这个消息，     我也很难过。           ← 逐token实时
                       │                          │
分句边界:           (句子1)                    (句子2)
                       │                          │
TTS:    [合成~350ms]→音频1██████  [合成]→音频2██████
                       │                          │
口型:                viseme流(跟音频1)         viseme流(跟音频2)
```

**同步锚点**：
- **字幕 ↔ token**：字幕直接跟 token，零延迟。
- **音频 ↔ 分句**：每个分句触发一次 TTS 合成，首音频延迟 = 分句累积时间 + TTS 合成时间。
- **口型 ↔ 音频**：口型严格跟音频，偏移 < 50ms（用音频时间戳对齐）。
- **字幕 ↔ 音频**：字幕领先音频（字幕先显示，音频随后播）。这是设计选择——用户能"预读"即将说出的内容，体验更自然。TTS 播完后字幕右移（§4.4.2）。

### 5.4 β 路径预合成缓存

主脑是外部 API，无"本地 KV Cache 复用"概念（旧架构的 prefix KV 复用不再适用）。但 β 路径的"TTS 预合成缓存"仍然有效——M3 在 β 路径预生成候选回复（带 W_probe 过滤）后，M4 可预合成 TTS 音频缓存，时机到直接播放：

```python
class BetaPreSynthCache:
    def __init__(self):
        self._audio_cache: Dict[str, bytes] = {}  # sentence_hash → audio

    async def maybe_use_cache(self, sentence: str) -> Optional[bytes]:
        """β 路径预合成命中检查"""
        h = hash(sentence)
        return self._audio_cache.get(h)

    def pre_synthesize(self, sentence: str, audio: bytes, ttl=120):
        """β 路径：M3 预生成 token 流后，M4 预合成 TTS"""
        self._audio_cache[hash(sentence)] = audio
        asyncio.get_event_loop().call_later(ttl,
            lambda: self._audio_cache.pop(hash(sentence), None))
```

**β 预合成失效条件**：用户开口（α 路径启动）→ β 所有预合成作废；超时（120s）→ 自然过期。

### 5.5 端到端时延分解

α 路径首音频端到端时延分解（新架构，主脑为 API）：

```
[用户开口]                              t=0
   │ VAD 检测                          +300ms
   ▼ SpeechStartEvent → M2             t=0.3s
[ASR 流式首 chunk]                      t=0.3s
   │ M2 读 UserState + 检索            +80ms
   │ 语境组装 + 身份 prompt 序列化       +80ms
   ▼ M3 调主脑 API（流式）              t=0.46s
[主脑 API 首 token（网络+推理）]         t=0.46s + 1.5s = 1.96s（预算 2.0s ✓）
   │ 分句器累积首句（~10字）             +300ms
   │ （并行：M3 W_probe batch 检测，~10ms/batch 不显著阻塞）
   ▼ 首句送 TTS                        t=2.26s
[TTS 首音频]                            t=2.26s + 0.35s = 2.61s
   ▼ 扬声器播放
[首音频端到端]                          ≈ 2.61s
```

**优化后（目标值）**：
- ASR 首 chunk 300ms（VAD 即推，M2 提前启动）→ M3 调 API 提前到 0.46s
- 主脑 API 首 token 1000ms（目标值，需 API 提供商就近接入 + 简化 prompt）→ 1.46s
- 分句 + TTS 首 audio 650ms → **首音频 ≈ 2.11s**（目标 2.0s，预算 2.5s ✓）

**关键杠杆**：
1. VAD 即推 SpeechStartEvent（让 M2/M3 提前启动，省 ~300ms 等待 ASR 完整文本）
2. 主脑 API 首 token 优化（M3 职责：精简身份 prompt、就近接入点、备用 API 切换）
3. 首句 ≤15 字（让分句器早切，TTS 早开始合成）
4. TTS 流式合成（不等整句合成完，首 audio 200–500ms 即出）

## 6. 视觉感知子系统详解

视觉感知 4 个子任务全部在本地 CPU 运行，**不抢副脑 GPU**（副脑 GPU 跑 Qwen2.5-3B + V30 的状态感知/异己检测/身份维持 forward），总延迟 < 100ms，旁路运行不阻塞 α 路径。

### 6.1 人脸检测与追踪（MediaPipe）

| 候选 | 速度 | 精度 | 模型大小 | 选型决定 |
|---|---|---|---|---|
| MediaPipe Face Detection | 5–15ms | 中（单人优） | 1.5MB | **首选** |
| OpenCV DNN + SSD | 15–30ms | 中 | 5MB | 备选 |
| MTCNN | 50–100ms | 高 | 12MB | 不选（太慢） |
| YOLOv8-face | 20–40ms | 高 | 6MB | 备选（GPU 才快） |

**选 MediaPipe**：CPU 即可 5–15ms，满足 30FPS 实时；自带 landmark 输出便于后续情绪/注意力复用。

```python
import mediapipe as mp

class MediaPipeFaceDetector:
    def __init__(self):
        self.detector = mp.solutions.face_detection.FaceDetection(
            model_selection=1, min_detection_confidence=0.6)
        self.tracker = mp.solutions.face_mesh.FaceMesh(
            max_num_faces=1, refine_landmarks=True)  # 468 关键点

    async def detect(self, frame):
        rgb = cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)
        res = self.detector.process(rgb)
        if not res.detections:
            return []
        faces = []
        for d in res.detections:
            bbox = d.location_data.relative_bounding_box
            faces.append(Face(bbox=self._to_abs(bbox, frame.shape),
                              score=d.score[0]))
        # landmark 追踪（用于情绪/注意力）
        mesh = self.tracker.process(rgb)
        if mesh.multi_face_landmarks:
            for f, lm in zip(faces, mesh.multi_face_landmarks):
                f.landmarks = lm.landmark  # 468 个 3D 点
        return faces
```

### 6.2 情绪识别（FERPlus，<100ms）

情绪识别基于已检测的 468 个 face landmark + RGB 裁剪，用轻量 CNN 分类 7 类（neutral/happy/sad/angry/surprise/fear/disgust）。

**选型**：FERPlus-Hub 预训练 MobileNetV2（ONNX，CPU 推理 ~20ms），输出 7 类概率。不用大模型（如 HSEmotion）因为延迟超标。

```python
class FERPlusEmotionClassifier:
    EMOTIONS = ["angry","disgust","fear","happy","sad","surprise","neutral"]
    def __init__(self):
        self.sess = ort.InferenceSession("ferplus_mobilenetv2.onnx",
                                          providers=["CPUExecutionProvider"])
    async def classify(self, frame, faces):
        if not faces: return None
        face_img = self._crop_align(frame, faces[0])  # 64x64 灰度
        probs = self.sess.run(None, {"input": face_img})[0][0]
        idx = int(np.argmax(probs))
        return Emotion(label=self.EMOTIONS[idx],
                       confidence=float(probs[idx]))
```

**时序平滑**：单帧情绪抖动大，用滑动窗口（5 帧）多数投票，避免"瞬时惊讶"误判。

### 6.3 presence 检测（用户在场）

presence 是"用户是否在摄像头视野内"的布尔信号，由人脸检测派生：

```python
class PresenceChecker:
    def __init__(self):
        self._absent_frames = 0
        self._present_frames = 0
        self._state = False
    def check(self, faces) -> bool:
        # 滞回判定，避免边界抖动
        if faces:
            self._present_frames += 1
            self._absent_frames = 0
            if not self._state and self._present_frames >= 3:  # 连续3帧
                self._state = True
        else:
            self._absent_frames += 1
            self._present_frames = 0
            if self._state and self._absent_frames >= 30:  # 连续1s缺席
                self._state = False
        return self._state
```

**滞回阈值**：进入需连续 3 帧（100ms），离开需连续 30 帧（1s）。避免有人侧身瞬间被误判离开。

### 6.4 注意力估计（gaze，看向 Lucy 的程度）

注意力 = 用户是否看向 Lucy（摄像头）。基于 face mesh 的**眼部 landmark + 头部姿态**估计注视方向：

```python
class GazeAttentionEstimator:
    # MediaPipe mesh 中虹膜关键点索引
    LEFT_IRIS = [468, 469, 470, 471, 472]
    RIGHT_IRIS = [473, 474, 475, 476, 477]
    LEFT_EYE_CORNERS = [33, 133]
    RIGHT_EYE_CORNERS = [362, 263]

    def estimate(self, frame, faces) -> float:
        if not faces or not faces[0].landmarks:
            return 0.0
        lm = faces[0].landmarks
        # 虹膜中心相对眼角的比例 → 注视方向
        lr = self._iris_ratio(lm, self.LEFT_EYE_CORNERS, self.LEFT_IRIS)
        rr = self._iris_ratio(lm, self.RIGHT_EYE_CORNERS, self.RIGHT_IRIS)
        gaze_x = (lr + rr) / 2  # 0=极左, 0.5=正中, 1=极右
        # 头部 yaw（用鼻尖-左耳-右耳估）
        yaw = self._estimate_yaw(lm)
        # 注视中央 + 头部正向 = 高注意力
        att = self._fuse(gaze_x, yaw)  # 0..1
        return float(np.clip(att, 0, 1))
```

**输出语义**：
- `attention > 0.7`：用户正看向 Lucy（适合主动发起对话）
- `0.3 < attention ≤ 0.7`：用户分心（看屏幕/手机）
- `attention ≤ 0.3`：用户转头/离开

## 8. 与 M1/M2/M3/M6 的耦合

### 8.1 输入侧耦合（推 M1/M2）

| 推送方向 | 事件 | 主题 | 协议 | 时机 |
|---|---|---|---|---|
| M4 → M2 | SpeechStartEvent | `m2.speech_start` | 可靠队列 + ACK | VAD 检测到用户开口（不等 ASR 完整文本） |
| M4 → M2 | ASR 完整文本 | `m2.final_text` | 可靠队列 + ACK | ASR 返回 final |
| M4 → M1 | PresenceEvent | `m1.presence` | 最佳努力 | presence 状态变化（滞回判定后） |
| M4 → M1 | VisualState | `m1.visual_state` | 最佳努力 | 10Hz 持续推送 |
| M4 → M1 | AttentionEvent | `m1.attention` | 最佳努力 | attention 跨阈值 |
| M4 → M1 | EmotionShiftEvent | `m1.emotion_shift` | 最佳努力 | 情绪类切换 |

**契约一致性**（对齐主文档 §5.6）：
- SpeechStartEvent 丢失会导致 α 路径不启动——必须保证投递（可靠队列）
- VisualState 丢一帧不影响功能——最佳努力即可

### 8.2 输出侧耦合（接 M3 token 流 + 推 M6 音频特征）

| 接收/推送方向 | 数据 | 主题/接口 | 协议 | 时机 |
|---|---|---|---|---|
| M3 → M4 | TokenChunk（干净 token） | `m3.token_stream` | 流式订阅 | M3 W_probe 过滤后逐 token 推 |
| M3 → M4 | AlienReport（异己汇总） | `m3.alien_report` | 流结束一次性 | M4 仅记录用于评估，不处理 |
| M4 → M6 | viseme + amplitude + f0 | `m6.viseme` | 最佳努力 | 每 20–50ms 推送 |
| M4 → 前端 | 字幕 token | `frontend.subtitle.token` | WebSocket | 逐 token 立即推 |
| M4 → 前端 | 字幕播完标记 | `frontend.subtitle.played` | WebSocket | TTS 句末音频播完 |
| M4 → 前端 | TTS 音频 | `frontend.tts_audio` | WebSocket（二进制） | TTS 流式音频 chunk |
| M4 → 前端 | 思考步骤 | `frontend.thinking.step` | WebSocket | M3 思考模式流式推送 |

**关键约束**：
- M4 从 M3 接收的 token 流是**已过滤异己的干净流**——M4 不做任何异己检测、缓冲、重生成
- M3 的 W_probe batch 检测与 API 流式接收并行，对 M4 透明（M4 看到的 token 流时序与直连 API 几乎一致，仅增加 ~10ms/batch 的副脑 forward，与 API 网络往返重叠）
- M4 → M6 的 viseme 信号是单向输出，M6 自主插值驱动，不反馈

### 8.3 与其他模块的边界

- **M1**：M4 是 UserState 中 `presence`/`attention`/`emotion` 字段的唯一数据源；M1 负责融合与长期建模。
- **M2**：M4 只推事件与接收输出指令，不参与决策。
- **M3**：M4 从 M3 接收干净 token 流，不直接调用主脑 API、不做异己检测。
- **M5**：M4 不直接调工具；网络搜索结果经 M2 → 前端展示（§7.7）。
- **M6**：M4 仅单向推 viseme 信号，不干涉 M6 控制环。

## 9. 时延管理与降级

M4 是系统对外唯一通道，降级必须保证"基础对话不中断"。降级策略对齐主文档 §8.1。

### 9.1 降级级与触发

| 降级级 | 触发 | 行为 | 用户感知 |
|---|---|---|---|
| L0 正常 | — | 全功能（主脑 API + 副脑 + 预计算 + 异己守卫 + 全模态） | 视觉+语音+文本 |
| L1 GPU 忙 | α 与 β 抢副脑本地 GPU | β 预计算暂停；α 的 W_probe 检测降频（每 32 token 一次而非 16） | 无感知（M3 内部） |
| **L2 主脑 API 慢** | 首 token >2s | **M3 跳过记忆检索，用最近 3 轮对话兜底**；身份 prompt 精简 | 略慢但回复不中断 |
| **L3 API 超时** | M3 >5s 无首 token | **M2 用规则兜底占位"让我想想..."，主脑 API 后台继续或转备用模型** | 听到占位语，避免干等 |
| **L4 多模态失效** | ASR/Vision 挂 | **降级为纯文本交互** | 失去语音输入/视觉感知，仍可文字对话 |
| **L5 身体失效** | M6 通讯断 | **身体冻结，对话继续；字幕补偿**（口型同步信号丢弃，字幕仍正常显示） | 形象不动，对话正常 |
| L6 副脑失效 | M2 崩溃 | 纯被动模式（用户输入→主脑 API 直连→输出，无主动、无身份守卫） | 失去主动发起 |
| L7 主脑 API 不可用 | API 401/403/网络断 | M3 切备用 API（OpenAI↔DeepSeek 互备）；全断时副脑本地 Qwen 应急生成（降级质量） | 略慢或风格略变 |

```python
        self.level = 0

            self.level = 2

            # M4 仍正常接收 token 流，时延略增
            await self.bus.publish("frontend.degradation", {"level": 2})

    async def on_api_timeout(self, event):
        """L3: M3 >5s 无首 token（M3 上报）"""
        if self.level < 3:
            self.level = 3
            # M4 视角：M2 推规则占位语 token 流（"让我想想..."）
            # M4 仍走流式管线，但 token 流来源从 M3 切到 M2 占位
            await self.bus.publish("frontend.degradation", {"level": 3})

    async def on_multimodal_fail(self, event):
        """L4: ASR/Vision 失效"""
        if self.level < 4:
            self.level = 4
            # M4 视角：禁用 ASR/Vision pipeline，仅保留文本输入
```

### 10.2 WebSocket 双向通信

前端与后端通过单一 WebSocket 长连接通信，消息类型复用事件总线主题：

```typescript
// useWebSocket hook
function useWebSocket() {
  const ws = useRef<WebSocket>();
  const handlers = useRef<Map<string, Set<Function>>>(new Map());

  useEffect(() => {
    ws.current = new WebSocket("ws://localhost:8000/ws/main");
    ws.current.onmessage = (e) => {
      const msg = JSON.parse(e.data);
      const hs = handlers.current.get(msg.type) ?? new Set();
      hs.forEach(h => h(msg.payload));
    };
    return () => ws.current?.close();
  }, []);

  const on = (type: string, h: Function) => {
    if (!handlers.current.has(type)) handlers.current.set(type, new Set());
    handlers.current.get(type)!.add(h);
    return () => handlers.current.get(type)!.delete(h);
  };
  const send = (type: string, payload: any) =>
    ws.current?.send(JSON.stringify({ type, payload }));

  return { on, send };
}

// 消息类型协议
type WSMessage =
  | { type: "subtitle.token"; payload: { token: string; sentence_id: number } }
  | { type: "subtitle.played"; payload: { sentence_id: number } }
  | { type: "tts.audio"; payload: { chunk: ArrayBuffer; sentence_id: number } }
  | { type: "m6.viseme"; payload: { viseme: string; amplitude: number } }
  | { type: "m2.avatar_action"; payload: { action: string } }
  | { type: "thinking.step"; payload: { text: string } }
  | { type: "search.results"; payload: { results: SearchResult[] } }
  | { type: "frontend.degradation"; payload: { level: number; msg?: string } };
```

### 11.1 流式管线主循环（M4 输出侧核心）

```python
# m4/output_pipeline.py
async def run_output_pipeline(receiver: TokenStreamReceiver, event_bus):
    """从 M3 接收干净 token 流，走分句→TTS→三路并行分发"""
    segmenter = SentenceSegmenter()
    tts = TTSStreamPipeline(VOLC_APP_ID, VOLC_TOKEN, voice_id="lucy_v1")

    async def sentence_stream():
        async for token in receiver.stream():
            # 字幕路：逐 token 立即推前端
            await event_bus.publish("frontend.subtitle.token",
                {"token": token, "sentence_id": segmenter.sentence_id})
            # 分句路：累积
            sub = segmenter.feed(token)
            if sub:
                yield sub
        if segmenter.buf:
            yield SubSent(text=segmenter.buf, id=segmenter.sentence_id)

    async def audio_route(audio_iter):
        async for chunk in audio_iter:
            # 音频送前端扬声器
            await event_bus.publish("frontend.tts_audio", chunk)
            # viseme 送 M6
            await event_bus.publish("m6.viseme", {
                "viseme": chunk.viseme, "amplitude": compute_rms(chunk.audio_bytes),
                "timestamp": time.monotonic()})
            # 该句播完 → 通知前端字幕右移
            if chunk.is_last_in_sentence:
                await event_bus.publish("frontend.subtitle.played",
                    {"sentence_id": chunk.sentence_id})

    audio_iter = tts.stream(sentence_stream())
    await audio_route(audio_iter)
```

## 13. 结论

模块4 是 Lucy 与外界对话的唯一感官与表达界面。架构反转后，M4 的核心改动是**输出侧 token 流来源从"本地 GPU 生成"改为"经 M3 从主脑 API 流式接收（已过滤异己）"**——M4 不再做任何异己检测，只负责把干净 token 流走流式管线变成可听可见的对话体验。设计核心仍是**流式管线的零等待编排**：

1. **输入侧三路并行（不变）**：ASR（流式，500ms 首 chunk）+ 视觉（4 任务旁路，<100ms 不阻塞副脑 GPU）+ 文本（25ms 入口），降维成结构化事件推送 M1/M2。
2. **输出侧流式管线（大改）**：M3 干净 token 流 → 分句器（标点 + 长度阈值）→ TTS 流式合成 → 三路并行分发（音频/字幕/口型），首音频端到端 ≈ 2.11–2.61s，满足 2.5s 预算。
3. **token 来源解耦**：M4 从 M3 接收已过滤异己的干净 token 流，不直连主脑 API、不做异己检测；M3 的 W_probe batch 检测与 API 流式接收并行，对 M4 透明。
4. **用户偏好落实**：avatar 居中合适大小不被截断（`object-contain` + `max-h-[50vh]`）；字幕置于 canvas 外（独立栏布局）；TTS 播完后字幕右移（三态状态机）；思考过程显示（深度推理模式 `ThinkingPanel`）。
5. **视觉感知全 CPU**：MediaPipe + FERPlus-MobileNetV2 + Gaze，不抢副脑 GPU。
6. **前端 React 18**：虚拟形象 + 实时字幕 + 思考过程 + 搜索结果，单 WebSocket 复用事件总线主题。
7. **降级完备**：从 L0 全功能到 L7 主脑 API 全断，8 级降级保证基础对话不中断；L2/L3/L4/L5 全部对齐主文档 §8.1。
8. **契约一致**：数据契约、时延预算、流式管线设计、三路径分离、降级策略、资源隔离全部对齐主文档 §4–§8。

M4 的流式管线是 α 路径首音频延迟的最大杠杆——通过 VAD 即推 SpeechStartEvent、token 边到边分句、TTS 流式合成、三路并行分发，把"主脑 API 生成完再 TTS"的串行模型改为"边生成边过滤边合成边播放"的流水线模型，从而在 2.5s 硬预算内交付具身的、全模态的、低延迟的对话体验。架构反转带来的"主脑 API 方差更大"风险，由 M3 的 W_probe 并行过滤 + M4 的流式管线重叠 + 多级降级兜底共同吸收。
